# 产品顶层设计（执行版）

## 目的

定义 BuildWise 在当前主实现和理想目标下的产品定位、核心对象、能力边界和主业务链路，作为产品设计、架构设计和研发治理的共同基线。

## 范围

本文档负责：

- 产品定位
- 目标用户
- 核心业务链路
- 平台对象模型的产品视角
- 能力边界与非目标
- 理想状态下的产品能力地图

本文档不负责：

- 技术分层细节
- 接口与数据结构细节
- 运维与投产操作步骤

## 关键结论

1. BuildWise 的本质不是聊天工具，而是“业务意图到可执行交付”的项目级工作台。
2. 产品最核心的长期边界是 `Tenant -> Project -> Iteration -> Knowledge`，不是单次会话。
3. 平台的价值链必须覆盖“分析、边界、交付物、测试、发布、知识沉淀”六个阶段，不能只停留在内容生成。
4. BuildWise 的理想状态是“业务人员可持续参与、技术团队可受控交付、项目知识可长期积累”。

## 1. 产品定位

BuildWise 是面向产品经理、业务负责人、技术负责人和 QA 的 AI 原生交付平台。  
它要解决的不是“再生成一份 PRD”，而是软件交付中最容易失真的三段链路：

1. 需求理解链路
2. 交付推进链路
3. 版本决策链路

平台的目标是让团队在每一轮迭代中都能明确回答：

- 本次需求到底影响什么
- 当前版本边界是否已经收敛
- 哪些测试和证据已经到位
- 这个版本现在是否具备发布条件
- 本轮经验是否已经沉淀为项目长期知识

## 2. 目标用户与使用角色

### 2.1 业务负责人

关注点：

- 需求是否被正确理解
- 风险和发布判断是否清晰
- 项目是否越来越懂业务

### 2.2 产品经理

关注点：

- 范围、边界与验收标准
- 版本推进是否可控
- 原型、交付物与测试是否对齐

### 2.3 技术负责人

关注点：

- 影响范围是否清晰
- 仓库、代码边界和发布门禁是否可控
- 模型与实现是否保持一致

### 2.4 QA

关注点：

- 验收标准是否已转成测试矩阵
- 阻断项是否明确
- 发布评审是否有证据基础

### 2.5 平台管理员

关注点：

- 租户与权限治理
- 运行时可用性
- 项目 workspace 与 Agent 执行策略

## 3. 产品核心对象

### 3.1 Tenant

Tenant 是访问与权限边界。  
一个用户可在多个租户间切换，但任何项目都必须归属某个租户。

### 3.2 Project

Project 是长期知识边界。  
它承载：

- 业务术语
- 稳定规则
- 组件与代码映射
- 决策日志
- 已知风险
- 发布历史

Project 不是“项目列表中的一条记录”，而是平台最重要的长期容器。

### 3.3 Iteration

Iteration 是版本推进边界。  
它承载某一次需求输入后的：

- 目标
- 范围
- 验收标准
- 上传材料
- 分析结论
- 交付物
- 测试矩阵
- 发布评审

### 3.4 Workspace

Workspace 是项目的运行边界。  
它是项目知识与 OpenClaw 上下文的承载空间，而不是一次会话的临时缓存。

### 3.5 Knowledge Base

Knowledge Base 是平台相对普通 AI 工具的核心差异。  
它必须长期保留并可检索：

- 业务规则本体
- 技术本体
- 决策与风险
- 变更模式
- 版本历史

## 4. 主业务链路

BuildWise 的理想主链路如下：

1. 登录并进入租户
2. 创建或进入项目
3. 绑定项目 workspace 与代码仓库
4. 创建迭代并填写范围和验收标准
5. 上传需求材料
6. AI 输出结构化分析与待确认问题
7. 人工确认理解与变更边界
8. 平台推进交付物、测试矩阵和发布评审
9. 满足门禁后发布或记录部署
10. 将新增知识沉淀到项目长期空间

平台必须保证：

- 每一步都能回看前因后果
- 每一步都能被后续测试和发布复用
- 每一次迭代都能增量沉淀，而不是重新开始

## 5. 核心能力地图

### 5.1 输入能力

支持多源输入：

- 自然语言需求
- 文档
- PDF/Word
- HTML
- 截图
- 原型文件夹
- 历史版本背景

理想状态要求：

- 平台能识别输入类型
- 为不同输入选择合适分析策略
- 对无文本材料提供降级分析与澄清机制

### 5.2 分析能力

平台应输出：

- 需求理解摘要
- 项目与产品识别
- 差异分析
- 优先级发现
- 澄清问题
- 风险提示
- 追溯映射基础信息

### 5.3 边界收敛能力

平台必须支持用户确认：

- requirement refs
- component refs
- code paths

这是后续测试、交付物和发布判断的共同边界基础。

### 5.4 交付推进能力

平台不仅要保存交付物，还要让交付物处于清晰阶段流中，例如：

- clarification
- scope
- interaction
- development
- testing
- release
- archive

### 5.5 测试与发布能力

平台必须把验收标准转成可执行测试矩阵，并产出发布评审：

- `go`
- `caution`
- `block`

发布判断必须依赖证据，而不是自由文本意见。

### 5.6 知识沉淀能力

平台必须让项目越做越懂业务，而不是每轮重新理解。  
理想状态下，所有迭代新增规则、映射和结论都会回写到项目知识库。

## 6. 理想状态下的产品特征

### 6.1 业务人员持续参与

业务人员不只是上传一次材料，而是能在原型、实现、测试和发布阶段持续补充规则与判断。

### 6.2 Agent 是治理参与者，不是自由生成器

AI 负责理解、归纳、评估和推进；  
平台负责：

- 提供项目上下文
- 强制关键确认点
- 守住发布门禁
- 记录审计轨迹

### 6.3 项目级记忆优先于会话记忆

任何长期有效的业务知识都必须回到项目空间，而不是只停留在某条对话里。

### 6.4 版本决策可证据化

版本是否可发，必须建立在：

- 已确认的边界
- 已执行的测试
- 已生成的评审
- 已确认的风险

而不是建立在“看起来问题不大”。

## 7. In Scope

当前执行版产品设计必须覆盖：

1. 多租户项目工作台
2. 项目/迭代管理
3. 材料上传与分析
4. 变更边界确认
5. 交付物阶段流
6. 测试矩阵与发布评审
7. 项目级知识沉淀
8. OpenClaw 非侵入式集成

## 8. Out Of Scope

以下内容不属于当前主产品目标：

1. 通用型聊天平台
2. 通用低代码页面生成器
3. 与项目边界无关的办公自动化平台
4. 复杂多 Agent 编排市场
5. 完全自动无人值守发布

## 9. 产品成功标准

理想状态下，平台应能稳定达成以下结果：

1. 需求上传后，团队能在一次分析轮内获得清晰影响评估和待确认点。
2. 任一迭代在进入测试前，已经明确 requirement/component/code 三向边界。
3. 任一发布结论都能追溯到测试、评审和风险证据。
4. 连续多个版本后，项目知识库能显著减少重复解释成本。
