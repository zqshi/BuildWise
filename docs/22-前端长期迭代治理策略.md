# 前端长期迭代治理策略

## 目的

- 回答“是否需要引入更多前端框架”的长期决策问题。
- 确保在持续迭代中，前端结构可维护、可扩展、可验证。

## 当前结论（2026-02-13）

- 基础框架保持：`React + TypeScript + Vite`。
- 现阶段不引入重型 UI 框架（如全量组件库替代），优先沉淀设计令牌与组件规范。
- 路由与数据层采用“按触发条件引入”的策略，不做一次性过度工程化。

## 何时引入额外前端框架

满足以下任一条件时，进入“框架升级评估”：

- 页面路由超过 8 个，且跨页面状态同步频繁。
- 同一接口请求在 3 个以上页面重复实现缓存/重试逻辑。
- 表单流程超过 5 个复杂场景（联动校验、分步、动态字段）。
- 组件复用率低于 40%，且样式重复明显增加。

## 升级优先级

1. `react-router-dom`：当路由规模扩大时引入，统一页面跳转与守卫。
2. `TanStack Query`：当异步状态复杂时引入，统一缓存、重试、失效策略。
3. 表单库（如 `react-hook-form`）：当复杂表单显著增多时引入。
4. UI 组件库：仅在设计系统无法支撑业务交付速度时评估引入。

## 结构治理红线

- 单文件行数必须受控（由 `npm run check:boundaries` 守卫）。
- 页面容器与展示组件分离：
  - 容器负责数据编排与副作用。
  - 展示组件负责渲染与交互输出。
- 禁止把领域规则直接写在样式文件和路由入口文件里。

## 文档治理红线

- 一个文档只承担一个主主题，禁止“大杂烩”。
- 文档行数受控（默认上限 220 行，超限必须拆分）。
- 设计、架构、流程、规范分文件维护，不跨文档混写职责。

## 执行机制

- 每次迭代前检查：
  - 目录结构是否仍满足边界定义。
  - 变更是否引入了重复模式（可抽象组件/Hook）。
- 每次提交前必须通过：
  - `npm run check:boundaries`
  - `npm run typecheck`
  - `npm run build`
