# 研发治理规范（DDD-TDD-质量门禁）

## 目的

定义 BuildWise 在需求进入、设计更新、开发实现、测试验证、文档同步和发布放行上的统一研发治理基线。

## 范围

适用于：

- 前端：`v2/src/**`
- 后端：`v2/backend/src/**`
- 脚本：`v2/scripts/**`、`v2/backend/scripts/**`
- 执行版文档：`docs/**`

## 关键结论

1. DDD + TDD 是默认研发范式，不是可选建议。
2. 任何行为变更都必须带自动化测试和相关文档更新。
3. 质量门禁必须覆盖边界、类型、构建、测试、文档一致性和生产准备度。
4. BuildWise 的治理重点不是“多跑命令”，而是确保产品、架构、实现、测试和门禁同步演化。

## 1. 研发流程基线

标准变更流程如下：

1. 识别问题与范围
2. 更新或确认相关设计文档
3. 编写失败测试
4. 实现最小变更
5. 重构并收口边界
6. 运行质量门禁
7. 更新文档和脚本
8. 记录风险、验证和回滚信息

任何跳过中间关键环节的做法都应视为例外，而不是常规。

## 2. 需求进入规范

任一需求进入开发前，必须明确：

- In scope
- Out of scope
- 验收标准
- 影响对象
- 风险点

对于 BuildWise，影响对象至少要覆盖：

- Project / Iteration 流程
- API 或契约
- 建模视图
- Change Control
- 测试矩阵
- 发布评审

## 3. DDD 执行规范

### 3.1 领域优先

新增行为必须先判断它属于哪个上下文：

- workspace
- governance
- platform
- continuous modeling

### 3.2 设计顺序

推荐顺序：

1. 定义领域对象或契约
2. 定义应用用例
3. 选择基础设施适配方式
4. 暴露接口
5. 更新前端消费方式

### 3.3 严禁事项

- 直接在路由里叠加核心业务判断
- 把业务规则放到工具函数里逃避分层
- 把多上下文逻辑堆进一个服务类

## 4. TDD 执行规范

### 4.1 最低要求

每个行为变更至少具备：

- 一个主路径测试
- 一个失败路径或边界路径测试

### 4.2 推荐测试层次

后端优先级：

1. 领域/应用层单元测试
2. 契约测试
3. 关键端到端脚本

前端优先级：

1. 纯 presenter/model 测试
2. controller 或 API 适配测试
3. 页面关键行为测试

### 4.3 契约要求

以下变更必须补契约测试：

1. 新增或改变核心 HTTP 路由
2. 改变状态码语义
3. 改变分析、测试、发布相关结构化输出

## 5. 文档同步规范

### 5.1 必须同步更新的场景

以下变更必须同时改文档：

1. 产品主流程变化
2. 架构边界变化
3. 统一模型变化
4. 追溯链变化
5. 质量门禁变化
6. 生产运行规则变化

### 5.2 最低要求

至少更新：

- 执行版设计文档
- README 或运行说明
- 必要的校验脚本说明

## 6. 质量门禁

### 6.1 前端门禁

```bash
cd v2
npm run check:hygiene
npm run check:boundaries
npm run typecheck
npm run build
npm test
```

### 6.2 后端门禁

```bash
cd v2/backend
npm run check:hygiene
npm run check:boundaries
npm run check:prompts
npm run check:prompts:replay
npm run check:agents
npm run check:skills
npm run typecheck
npm run build
npm run test
npm run test:contract
```

### 6.3 发布候选门禁

```bash
cd v2
npm run verify:all

cd v2/backend
npm run verify:prod-release
```

## 7. 文档与脚本门禁

以下内容也属于门禁范围，不是附属材料：

1. 执行版文档是否同步
2. 例外清单是否同步
3. 生产样例配置是否同步
4. 校验脚本是否覆盖新行为

## 8. 变更说明要求

每次重要变更说明必须包含：

1. In scope
2. Out of scope
3. 影响范围
4. 风险等级
5. 验证命令与结果
6. 回滚方式

## 9. 回滚规范

任何可能影响核心交付链路的变更，都要能回答：

- 如何停用
- 如何恢复旧行为
- 会影响哪些项目或迭代

如果无法说明回滚方式，则该变更不应进入发布候选。

## 10. 例外机制

允许例外，但必须满足：

1. 有明确原因
2. 有影响说明
3. 有时效性
4. 有后续收口计划

不允许长期把例外当成常态。

## 11. DoD 检查清单

- [ ] 影响范围已识别
- [ ] 相关执行版文档已更新
- [ ] 失败测试已先写或已补足
- [ ] 实现遵循 DDD 边界
- [ ] 边界守卫通过
- [ ] 类型检查通过
- [ ] 构建通过
- [ ] 相关测试通过
- [ ] 验证结果已记录
- [ ] 回滚方式已明确
