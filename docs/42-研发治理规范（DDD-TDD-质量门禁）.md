# 研发治理规范（DDD / TDD / 质量门禁）

## 目的

- 为后续迭代建立统一且可执行的研发规范，防止质量随迭代下降。
- 约束“需求 -> 设计 -> 开发 -> 验证 -> 文档沉淀”全过程。

## 适用范围

- 前端：`v2/src/**`
- 后端：`v2/backend/src/**`
- 规范文档：`docs/**`

## 架构策略（默认 DDD，允许有条件替代）

1. 默认策略：DDD 分层 + 模块边界守卫。
2. 允许替代：当模块业务复杂度低、生命周期短、协作人数少时，可采用“Feature Slice（按功能切片）”。
3. 替代前提：
- 必须在 ADR 记录选择原因、风险和退出条件。
- 不得破坏现有分层依赖规则和边界守卫。
- 必须保留可回滚路径。

## DDD 执行基线

1. 领域层只表达业务语义与规则，不依赖 HTTP/UI/存储实现。
2. 应用层只做用例编排，不承载协议细节。
3. 基础设施层只做适配，不写业务决策。
4. 接口层只做请求响应转换，不写领域规则。

## TDD 执行基线

1. 每个新增功能先写失败测试（至少一个主路径、一个失败路径）。
2. 测试失败后再写最小实现，确保测试转绿。
3. 转绿后再重构，重构不得改变测试语义。
4. 新增接口必须有契约测试覆盖核心状态码和错误分支。

## 质量门禁（提交前必须全绿）

1. 前端：`npm run check:boundaries && npm run typecheck && npm run build`
2. 后端：`npm --prefix backend run check:boundaries && npm --prefix backend run typecheck && npm --prefix backend run build && npm --prefix backend run test:contract`
3. 文档：单文档单主题、单文件默认不超过 220 行。

## 文件规模控制策略

1. 超过阈值时必须拆分，不允许以“临时放宽阈值”替代重构。
2. 拆分优先级：
- 先拆动作（actions）
- 再拆加载器（loaders）
- 再拆派生计算（derived）
- 最后拆状态（state）

## 里程碑沉淀要求

1. 每次迭代必须更新 `docs/milestones/review-*.md`。
2. 每次关键架构调整必须新增 ADR。
3. 每次异常回滚必须记录触发条件、影响范围、恢复结果。

## 执行检查清单（DoD）

- [ ] 边界守卫通过
- [ ] 类型检查通过
- [ ] 构建通过
- [ ] 契约测试通过
- [ ] 文档已更新
- [ ] 回滚路径已验证
