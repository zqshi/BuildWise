# 技术架构设计（执行版）

## 目的

定义 BuildWise 的目标架构、上下文边界、运行时拓扑、核心模块职责和演进方向，作为代码组织、接口设计和治理门禁的技术基线。

## 范围

本文档负责：

- 架构原则
- 上下文划分
- 前后端主模块职责
- 运行时拓扑
- 存储与知识物化设计
- 同步与异步执行边界

本文档不负责：

- 具体字段清单
- 详细接口逐项说明
- 运维执行步骤

## 关键结论

1. BuildWise 采用“项目级知识工作台 + 非侵入式 OpenClaw 集成”的架构，不改 OpenClaw 内核。
2. 平台主架构围绕三个中心展开：`Workspace Domain`、`Platform/Governance Domain`、`Knowledge Materialization`。
3. 技术实现必须把同步请求链路与异步分析/知识刷新链路显式分开。
4. 所有长期知识资产必须从运行时对象写回项目 workspace，而不是只保留在进程内存或单轮会话中。

## 1. 架构原则

1. DDD 分层优先：`domain -> application -> infrastructure -> interfaces`
2. 项目级知识优先于会话级拼接
3. 同步 API 负责状态推进，异步任务负责重分析、索引和定时汇总
4. OpenClaw 作为外部协作运行时接入，BuildWise 只做上下文注入和边界治理
5. 架构必须服务于“分析、边界、测试、发布、沉淀”主链路，而不是追求通用引擎复杂度

## 2. 逻辑上下文划分

### 2.1 Workspace Context

职责：

- 项目、迭代、消息、分析、变更控制、交付物、测试矩阵、发布评审

当前对应：

- `v2/backend/src/domain/workspace/**`
- `v2/backend/src/application/workspace/**`
- `v2/backend/src/interfaces/http/routes/workspace*.ts`

### 2.2 Platform / Governance Context

职责：

- 平台角色、权限、项目共享、模板、部署、审计、运维指标

当前对应：

- `v2/backend/src/application/platform/**`
- `v2/backend/src/application/workspace/governance*.ts`
- `v2/backend/src/interfaces/http/routes/platformRoutes.ts`

### 2.3 Continuous Modeling Context

职责：

- 持续建模候选、建模快照、业务/技术建模视图输出

当前对应：

- `v2/backend/src/application/continuousModeling/**`
- `v2/backend/src/domain/continuousModeling/**`

### 2.4 OpenClaw Integration Context

职责：

- Agent 运行适配
- session key 约定
- skills 注入
- workspace 绑定

当前对应：

- `v2/backend/src/application/workspace/openclaw*.ts`
- `v2/backend/src/infrastructure/openclaw/**`

## 3. 运行时拓扑

理想运行时由以下节点组成：

1. Web Frontend
2. BuildWise Backend API
3. Workspace Storage
4. Project Workspace File System
5. OpenClaw Gateway / Agent Runtime
6. LLM Provider

### 3.1 Frontend

职责：

- 呈现项目工作台
- 承接用户输入
- 渲染建模、交付、测试和评审信息
- 管理本地视图态和少量缓存

前端不应承担：

- 业务规则判定
- 追溯计算
- 发布门禁判定

### 3.2 Backend API

职责：

- 领域状态推进
- 分析任务编排
- 权限校验
- 项目知识物化
- 对外提供统一 `/api/v1` 接口

### 3.3 Workspace Storage

职责：

- 持久化项目、迭代、权限、部署、测试与审计数据

当前支持：

- `json`
- `sqlite`

目标要求：

- 业务逻辑不依赖具体存储实现
- 生产环境默认使用 `sqlite`

### 3.4 Project Workspace File System

职责：

- 存放 `.buildwise/` 项目知识资产
- 作为 OpenClaw 与 BuildWise 的共享上下文根

### 3.5 OpenClaw Gateway / Agent Runtime

职责：

- 执行对话与 skills 链路
- 维持 session/history

BuildWise 不应侵入其内部工作流引擎，只应提供：

- 项目上下文
- knowledge hit
- policy constraints

### 3.6 LLM Provider

职责：

- 负责分析、归纳、建议和部分运维辅助输出

平台需要对其做：

- 启动探针
- 可达性检查
- 降级与失败语义封装

## 4. 前端架构

### 4.1 分层

- `src/domain`：前端领域类型
- `src/app`：应用编排和页面级用例胶水
- `src/infrastructure`：HTTP、鉴权和外部访问
- `src/shared`：纯工具
- `src/pages`：页面与视图组件
- `src/contexts`：跨页面状态容器

### 4.2 理想职责边界

`App.tsx` 只负责主视图装配，不继续吸收具体业务逻辑。  
每个页面模块应拆成：

- view
- presenter/model
- hook/action

### 4.3 前端关键能力模块

1. 身份与租户切换
2. 项目总览
3. 迭代工作区
4. 建模视图
5. OpenClaw 协作视图
6. 权限治理视图

## 5. 后端架构

### 5.1 分层

- `domain`：类型、值对象、仓储接口、状态机
- `application`：用例编排与领域组合
- `infrastructure`：存储、运行时、外部依赖适配
- `interfaces`：HTTP 路由与请求响应映射

### 5.2 应用服务拆分原则

单个应用服务应围绕单一子能力组织，例如：

- analysis
- change control
- iteration
- project
- governance
- quality
- openclaw

避免把所有流程重新堆回一个巨型 orchestrator。

### 5.3 路由组织原则

`workspaceRoutes` 只做路由组合，不写业务逻辑。  
具体职责分散到：

- project routes
- iteration core routes
- iteration change control routes
- policy routes
- platform routes

## 6. 存储设计

### 6.1 事务型状态存储

承载：

- projects
- iterations
- messages
- change control
- permissions
- deployments
- audit logs

### 6.2 文件型知识存储

承载：

- workspace summary
- ontology docs
- decisions docs
- release history
- shards
- vector-like index

### 6.3 设计原则

事务型存储负责“状态真实源”；  
文件型知识存储负责“项目长期记忆和召回”。  
二者不能相互替代。

## 7. 同步与异步链路

### 7.1 同步链路

适合：

- 登录
- 项目/迭代创建
- 状态更新
- 交付物提交
- 测试矩阵更新
- 发布评审读取

### 7.2 异步链路

适合：

- 大材料分析
- 分块分析
- 知识索引刷新
- 每日汇总
- 大型运维校验

### 7.3 目标要求

异步链路必须具备：

- job id
- 状态查询
- 超时语义
- 幂等与重试机制

## 8. Session 与 Workspace 设计

理想 session key 分层：

1. 全局对话：`global`
2. 项目对话：`project-<projectId>`
3. 迭代执行：`project-<projectId>-iteration-<iterationId>`

约束：

- Project 是知识边界
- Iteration 是运行上下文
- Workspace 是文件和记忆边界

任一实现都不得把“全局对话”误当“项目知识空间”。

## 9. API 设计原则

1. 路由按业务对象聚合，不按技术动作堆叠
2. 所有写操作必须具备权限语义
3. 所有关键失败必须返回明确的阻断原因
4. 分析、测试和发布相关接口必须输出结构化数据，而不是纯文本

## 10. 观测与运行时

平台至少需要以下可观测性能力：

1. `/health`：liveness
2. `/ready`：readiness
3. `/api/v1/status`：运行时摘要
4. `/metrics`：Prometheus 指标
5. 审计日志
6. 关键任务日志

理想状态下，任何发布阻断都可以追溯到：

- 运行时状态
- 测试结果
- 发布评审
- 仓库健康

## 11. In Scope

1. 项目工作台单体前后端架构
2. 非侵入式 OpenClaw 集成
3. 项目级知识物化
4. 发布与治理指标
5. DDD 分层落地

## 12. Out Of Scope

1. 重写 OpenClaw
2. 引入复杂分布式微服务体系
3. 自建向量数据库优先于当前文件索引体系
4. 脱离项目边界的通用多 Agent 调度平台
