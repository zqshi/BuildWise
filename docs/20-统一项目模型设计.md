# 统一项目模型设计

## 目的

定义 BuildWise 的统一项目模型，保证产品、接口、存储、追溯、知识沉淀和发布门禁围绕同一套对象体系演化。

## 范围

本文档负责：

- 平台核心对象定义
- 对象关系与生命周期
- 关键约束与不变量
- 执行版最小字段结构

本文档不负责：

- 具体数据库建表实现
- HTTP 接口逐项字段说明
- UI 展示文案

## 关键结论

1. BuildWise 的统一模型核心不是“页面生成模型”，而是“项目级交付模型”。
2. `Project` 是长期知识边界，`Iteration` 是版本运行上下文，`Workspace` 是项目级运行与知识落盘边界。
3. 业务知识、技术知识、交付物、测试结果和发布结论都必须能回挂到项目或迭代，而不是漂浮在会话中。
4. 追溯、发布门禁和知识库都依赖该模型，任何对象改动都必须同步更新相关文档与测试。

## 1. 对象总览

统一项目模型由以下一级对象组成：

1. Tenant
2. Project
3. ProjectWorkspaceBinding
4. Iteration
5. IterationChangeControl
6. IterationArtifactWorkflow
7. AnalysisReport
8. KnowledgeBase
9. ModelView
10. ReleaseReview
11. Deployment
12. GovernancePolicy

## 2. 核心关系

### 2.1 Tenant -> Project

- 一个 Tenant 下可以有多个 Project
- 一个 Project 必须且只能归属一个 Tenant

### 2.2 Project -> Iteration

- 一个 Project 下可以有多个 Iteration
- 任一 Iteration 只能归属一个 Project
- Iteration 可继承前一版本的决策、风险和建模基线

### 2.3 Project -> Workspace Binding

- 一个 Project 在任一时刻只能有一个有效 workspace binding
- 同一路径不得同时绑定给多个 Project

### 2.4 Project -> KnowledgeBase

- 一个 Project 对应一份长期知识基线
- 多个 Iteration 共享并持续回写这份知识

### 2.5 Iteration -> Change Control

- 每个 Iteration 必须有变更控制对象
- Change Control 是测试矩阵、发布评审和代码边界的共同入口

### 2.6 Iteration -> Artifact Workflow

- 一个 Iteration 可以有多个交付物
- 交付物必须纳入阶段流，不允许只保存静态内容不保留状态

## 3. Project 模型

### 3.1 责任

Project 负责表达长期项目边界，而不是单次需求记录。

### 3.2 必备字段

- `id`
- `tenantId`
- `name`
- `description`
- `status`
- `ownerUserId`
- `repository`
- `knowledgeBase`
- `currentUserRole`
- `createdAt`
- `updatedAt`

### 3.3 关键约束

1. Project 必须存在租户归属。
2. Project 删除默认采用归档，不直接物理删除。
3. Project 的知识库与 workspace binding 必须保持一致。

## 4. ProjectWorkspaceBinding 模型

### 4.1 责任

用于把 Project 与 OpenClaw/文件系统工作区绑定。

### 4.2 必备字段

- `projectId`
- `openclawProfile`
- `agentId`
- `workspacePath`
- `runtimeMode`
- `locked`
- `createdBy`
- `createdAt`
- `updatedAt`

### 4.3 关键约束

1. `workspacePath` 建议使用绝对路径。
2. 同一路径不可复用到不同项目。
3. 绑定生效后必须能生成 `.buildwise/`。

## 5. Iteration 模型

### 5.1 责任

表达一次版本推进的完整上下文。

### 5.2 必备字段

- `id`
- `projectId`
- `version`
- `name`
- `description`
- `goals`
- `scope`
- `status`
- `progress`
- `continuity`
- `assessment`
- `changeControl`
- `createdAt`
- `updatedAt`

### 5.3 范围模型

`scope` 至少包含：

- `inScope`
- `outOfScope`
- `acceptanceCriteria`

### 5.4 继承模型

`continuity` 至少包含：

- `inheritedFromIterationId`
- `inheritedSummary`
- `carriedGoals`
- `carriedRisks`
- `carriedDecisions`

### 5.5 关键约束

1. 任一 Iteration 必须归属 Project。
2. 任一 Iteration 必须有范围和验收标准。
3. 没有 Change Control 的 Iteration 不允许进入发布判断。

## 6. IterationChangeControl 模型

### 6.1 责任

统一承接分析确认、边界、测试矩阵、发布评审和确认状态。

### 6.2 必备字段

- `pendingHumanConfirmation`
- `clarificationQuestions`
- `clarificationDraftResolvedQuestions`
- `clarificationRounds`
- `boundary`
- `generatedTestMatrix`
- `lastReleaseReviewDecision`
- `lastReleaseReviewReason`
- `lastReleaseReviewBlockers`
- `confirmedAt`
- `lastClarificationResolution`

### 6.3 Boundary 结构

- `requirementRefs`
- `componentRefs`
- `codePaths`
- `note`

### 6.4 关键约束

1. 若 `pendingHumanConfirmation=true`，发布必须阻断。
2. Boundary 未确认前，交付物和测试只能作为草稿推进。
3. 发布评审必须引用 Boundary 与测试矩阵结果。

## 7. AnalysisReport 模型

### 7.1 责任

承接一次材料输入后的结构化理解结果。

### 7.2 必备信息

- `understanding`
- `projectDetection`
- `meaningfulFindings`
- `prioritizedFindings`
- `clarificationQuestions`
- `traceabilityMap`
- `versionDiff`
- `risks`
- `suggestions`
- `releaseReview`
- `domainKnowledge`
- `qualityArtifacts`

### 7.3 关键约束

1. AnalysisReport 是 Change Control 的输入，不是直接发布依据。
2. AnalysisReport 需要人工确认后才能进入正式边界。

## 8. IterationArtifactWorkflow 模型

### 8.1 责任

承接交付物在各阶段的状态，而不是只保存一段内容。

### 8.2 必备对象

单个 Artifact 至少包含：

- `id`
- `title`
- `stage`
- `status`
- `content`
- `draft`
- `commits`
- `confirmations`
- `evidence`
- `updatedAt`

### 8.3 Stage 枚举

- `clarification`
- `scope`
- `interaction`
- `development`
- `testing`
- `release`
- `archive`

## 9. KnowledgeBase 模型

### 9.1 责任

承接 Project 的长期业务与技术记忆。

### 9.2 必备结构

- `ontologyTerms`
- `stableRules`
- `componentInventory`
- `codeMap`
- `decisionLog`
- `knownRisks`
- `changePatterns`
- `updatedAt`

### 9.3 关键约束

1. KnowledgeBase 按 Project 维护，不按 Iteration 维护。
2. 任何跨迭代稳定事实都应优先写入 KnowledgeBase。

## 10. ModelView 模型

### 10.1 责任

面向前端项目建模展示，统一输出业务摘要、实体、规则、关系和证据。

### 10.2 必备结构

- `projectId`
- `projectName`
- `iterationId`
- `ontologyTerms`
- `rules`
- `entities`
- `relations`
- `reviewTasks`
- `evidence`

### 10.3 目标作用

用于让产品、业务和技术基于同一份模型视图讨论，而不是各自维护解释。

## 11. ReleaseReview 模型

### 11.1 责任

表达一次版本在发布前的结构化判断。

### 11.2 必备字段

- `decision`
- `score`
- `blockers`
- `recommendations`
- `generatedAt`
- `evidenceRefs`

### 11.3 关键约束

1. `decision` 只允许为 `go | caution | block`
2. `block` 必须给出 blocker 列表
3. 发布记录必须引用最近一次 ReleaseReview

## 12. Deployment 模型

### 12.1 责任

表达部署意图、状态和结果。

### 12.2 必备字段

- `id`
- `projectId`
- `iterationId`
- `environment`
- `version`
- `status`
- `createdAt`
- `updatedAt`

### 12.3 关键约束

1. 生产部署应受仓库远端状态和 ReleaseReview 双门禁控制。
2. Deployment 只记录结果，不替代发布评审。

## 13. GovernancePolicy 模型

### 13.1 责任

表达平台或项目级执行策略与治理约束。

### 13.2 分层

- 全局策略
- 项目策略

### 13.3 最小字段

- `projectId`
- `version`
- `status`
- `strategy`
- `createdBy`
- `createdAt`

## 15. In Scope

1. 项目与迭代主对象
2. 长期知识对象
3. 变更控制与发布评审对象
4. 工作区绑定对象

## 16. Out Of Scope

1. 具体数据库表结构
2. 前端局部视图态
3. 临时缓存字段
