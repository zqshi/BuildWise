# DDD+TDD 与 1000 行治理最高声明

## 目的

把 BuildWise 的工程治理升级为最高优先级约束，确保产品、架构、实现、测试和文档长期保持可控，不因迭代推进而持续退化。

## 范围

适用于：

- 代码
- 脚本
- 执行版文档
- 测试资产
- 质量门禁和例外治理

## 关键结论

1. DDD + TDD 是最高原则，任何变更都不得绕过。
2. 单文件 1000 行是硬上限，超限只能作为短期例外，不得成为常态。
3. 文档与实现同步更新是强制要求，不是善意建议。
4. 所有例外都必须可见、可解释、可收口。

## 1. 最高原则

### 1.1 DDD + TDD 强制执行

必须满足：

- 领域边界清晰
- 用例编排清晰
- 协议层不承载业务规则
- 任何行为变化都有自动化测试支撑

禁止：

- “先实现后补测试”成为默认流程
- 用工具文件掩盖跨层依赖

### 1.2 单文件 1000 行硬上限

适用对象：

- 代码文件
- 脚本文件
- 文档文件

规则：

1. 新增超限文件一律禁止。
2. 存量超限文件必须进入例外清单。
3. 进入例外清单不代表可以继续扩张。

### 1.3 单文件单职责

每个文件只能围绕一个主主题展开。  
若出现以下现象，视为职责失控：

- 既有业务规则又有协议适配
- 既有页面渲染又有长链路状态编排
- 既有产品目标又有运行步骤又有治理规则

### 1.4 文档与实现同步

以下变更若未同步更新文档，视为不完整交付：

- 产品流程变化
- 架构边界变化
- 统一模型变化
- 追溯结构变化
- 发布门禁变化

## 2. 例外机制

### 2.1 例外适用范围

允许例外的场景只有两类：

1. 存量超限文件尚未完成拆分
2. 外部依赖或历史结构导致短期无法完全收口

### 2.2 例外必备信息

任一例外必须记录：

- 文件名
- 当前规模
- 为什么暂时不能拆
- 风险是什么
- 预计如何收口

### 2.3 例外失效条件

若出现以下情况，应立即视为治理失败：

- 例外文件继续明显扩张
- 例外持续多个迭代没有收口动作
- 例外被当成新增功能默认落点

## 3. 文件规模治理

### 3.1 默认目标

- 文档建议优先控制在 700 行以内
- 代码文件建议尽量低于 400 行
- 组件/控制器类文件应尽量低于 300 行

### 3.2 拆分优先级

当文件接近阈值时，优先拆：

1. 独立子能力
2. 输入解析
3. 输出构建
4. 状态派生
5. 视图层辅助模型

### 3.3 禁止的伪拆分

以下不算有效拆分：

- 仅把代码复制到新文件
- 拆出没有清晰职责的 `helpers`
- 只拆名字，不拆边界

## 4. 测试与质量要求

### 4.1 最低测试要求

行为变更必须至少配套：

- 一个主路径测试
- 一个失败或边界路径测试

### 4.2 契约测试优先级

以下能力必须优先保证契约测试：

- auth
- project / iteration
- analysis
- change control
- release review
- deployment

### 4.3 质量门禁不可跳过

以下门禁在发布候选阶段不得跳过：

- hygiene
- boundaries
- typecheck
- build
- tests
- contract
- prod readiness

## 5. 文档治理要求

### 5.1 执行版文档必须真实

执行版文档不是愿景墙，必须：

- 可落实
- 可对应到当前实现
- 可作为后续变更基线

### 5.2 历史稿不得污染执行版事实

历史稿可以保留，但不得与执行版混淆。  
冲突时，以执行版为准。

## 6. 变更影响分析要求

任意中高影响变更前必须分析：

- 模块影响
- API 影响
- 数据影响
- 配置影响
- 运行时影响
- 测试影响
- 文档影响

若不做该分析，则不满足工程治理要求。

## 7. 当前治理对象

BuildWise 当前治理重点不只是代码，还包括：

- OpenClaw 集成边界
- 项目 workspace 知识物化
- 运行时鉴权与健康检查
- 发布门禁
- 文档和脚本同步性

## 8. 执行方式

必须依赖自动化机制执行：

- `check-boundaries`
- `check-hygiene`
- `typecheck`
- `build`
- `test`
- `test:contract`
- `verify:prod-release`

只靠人工约束不算完成治理。

## 9. 责任要求

任何提交者都必须对以下内容负责：

1. 变更边界是否清晰
2. 测试是否覆盖
3. 文档是否同步
4. 是否引入新的超限文件
5. 是否扩大已有例外风险

## 10. 违反原则时的默认处理

若变更违反本声明，默认处理方式为：

1. 不合并
2. 或回退到受控范围内重新提交

“先合并后治理”不能作为长期默认方式。
