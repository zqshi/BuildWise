# 迭代窗口交互设计（定稿）

> 状态：已确认 | 日期：2026-03-27

---

## 一、产品本质

BuildWise 的核心赌注不在"AI 能不能写代码"，而在能不能建立并维护一条从"业务意图"到"技术实现"的活的知识链条（本体），让 AI 教练在这条链条上持续陪伴，而不是每次从零猜。

没有本体，AI 辅助开发永远停留在"高级补全"层面。有了本体，AI 是"带记忆的搭档"。

---

## 二、业务价值

| 用户痛点 | BuildWise 怎么解 | 本体的角色 |
|---|---|---|
| 每次跟新人/新工具解释业务背景要半天 | 系统自动积累业务知识，Agent 天然了解你的业务 | Agent 的业务记忆 |
| 需求文档写了一堆但跟代码对不上 | 每个交付物都锚定到本体实体上，需求→代码可追溯 | 追溯链的骨架 |
| 测试覆盖了 80% 代码但漏了关键业务规则 | 测试基于本体覆盖率生成，不是基于代码覆盖率 | 质量度量的标尺 |
| 上一版做了什么改了什么，过两个月就忘了 | 每轮迭代自动更新本体快照，形成版本化业务模型 | 跨迭代的知识载体 |
| 业务方说的"订单"和技术说的"order"是一回事吗 | 本体维护业务术语→技术术语的双向映射 | 业务-技术的翻译层 |

## 三、产品全流程（4 个用户感知阶段）

```
┌──────────────────────────────────────────────────────────┐
│                    本体（持续生长，用户无感）                │
│  ┌─────┐    ┌─────┐    ┌─────┐    ┌─────┐               │
│  │术语 │────│实体 │────│关系 │────│规则 │               │
│  └─────┘    └─────┘    └─────┘    └─────┘               │
│      ▲           ▲           ▲           ▲                │
│      │           │           │           │                │
│  ┌───┴───┐  ┌───┴───┐  ┌───┴───┐  ┌───┴───┐            │
│  │ 说清楚 │→│ 定边界 │→│ 做出来 │→│ 交出去 │            │
│  └───────┘  └───────┘  └───────┘  └───────┘            │
│   阶段一      阶段二      阶段三      阶段四              │
└──────────────────────────────────────────────────────────┘
```

### 阶段一：说清楚（理解与建模）

用户告诉系统"我要做什么"——可以是一句话、一份 PRD、一张截图、一段语音转文字。

交付物：
- 需求分析报告
- 产品需求文档

### 阶段二：定边界（范围锁定与规划）

用户跟 Agent 确认"这一轮做哪些、不做哪些"。

交付物：
- 边界确认

### 阶段三：做出来（开发与构建）

Agent 产出技术方案和代码，用户可随时补充业务规则。

交付物：
- 原型与交互
- 设计规范
- 技术架构
- 接口设计
- 数据模型设计
- 前端代码
- 后端代码

### 阶段四：交出去（验证与发布）

验证交付质量、批准发布、知识沉淀。

交付物：
- 测试矩阵
- 验收清单
- 发布评审
- 部署方案
- 交付归档

## 四、三个窗口职责

### 业务助手窗口（主窗口）

- 职责：维护 Skill 链编排（全局生效）、管理 Skills 的创建/调整
- 交互：纯自然语言对话
- 体现：编排变更日志 + 当前 Skill 链可视化

### 项目窗口

- 职责：本体图谱展示、跨迭代知识累积可视化、本体快照版本切换与 diff、项目健康度
- 交互：只看不聊（看板 + 知识库）
- 体现：实体关系图谱 + KPI 卡片 + 版本时间线
- 数据来源：服务层自动更新的 ProjectModelView API

### 迭代窗口

- 职责：日常工作场所，Agent 按 Skill 链推进流程
- 交互：自然语言对话 + 文件上传 + 交付物卡片点击
- 体现：对话流（自然语言 + 交付物卡片 + 变更影响警示条混排）

## 五、迭代窗口对话流设计

### 核心原则

1. 对话流 = 工作台，自然语言和交付物卡片混排显示
2. 不使用固定模板或固定流程，Agent 根据上下文决定何时产出什么
3. 交付物卡片是摘要态，点击打开抽屉查看详情
4. 本体处理全自动，用户无感

### 三类消息体

| 类型 | 触发条件 | 渲染方式 | 用户操作 |
|---|---|---|---|
| 自然语言 | Agent 正常回复 | 普通文本（支持 markdown） | 阅读 |
| 交付物卡片 | Skill 产出交付物 | 摘要卡片（标题+摘要+状态+按钮） | 点击 → 打开抽屉 |
| 变更影响警示条 | 本体变更影响已有交付物 | 黄色警示条（影响项+自动同步说明） | 仅阅读，不可交互 |

### 交付物卡片通用结构

```
┌─────────────────────────────────────────┐
│ {标题}                        待你确认   │
│                                         │
│ {摘要文本}                               │
│ · {关注点1}                              │
│ · {关注点2}                              │
│                                         │
│ [查看交付物]                             │
└─────────────────────────────────────────┘
```

- 点击 [查看交付物] → 打开右侧抽屉
- 抽屉内展示完整详情，支持编辑/确认操作
- 卡片出现时机和内容由 Agent + Skill 决定，前端只负责渲染

### 变更影响警示条结构

```
┌─ ⚡ 变更影响（{n} 项）────────────────┐
│ {受影响交付物1}·{受影响交付物2}·...    │
│ 已自动标记待同步                       │
└───────────────────────────────────────┘
```

- 触发条件：用户输入导致本体变更，且影响到已产出的交付物（status 为 partial 或 ready）
- 不可交互，仅视觉提醒
- 实现方式：Agent 回复中包含 `【变更影响】` 前缀标记，前端识别后渲染为警示条样式
- 复用现有 `【交付物引用】` 前缀解析机制

## 七、本体处理（服务层，全自动）

### 设计原则

- 本体的抽取、消歧、碰撞检测、规则关联、快照更新、KB 同步全部在服务层自动完成
- 用户不需要确认任何本体操作
- 不产出任何本体相关的卡片

### 自动处理流程

```
每次 Skill 执行时自动触发：
  ├── 本体抽取 → OntologyTerm / BusinessEntity / BusinessRelation / BusinessRule
  ├── 消歧 → 自动合并同义术语（新版优先）
  ├── 碰撞检测 → 自动消解冲突
  ├── 规则关联 → 用户口述的规则自动关联到实体/页面/API
  ├── 快照更新 → ModelSnapshot 自动升级版本
  ├── KB 同步 → ProjectKnowledgeBase 7 字段自动填充
  └── 视图投影 → ProjectModelView API 数据自动刷新
```

### 用户可感知的两个出口

1. **项目面板图谱**：静默刷新，用户打开项目面板即可看到最新本体图谱
2. **变更影响警示条**：仅当本体变更影响到已有交付物时，在对话流中显示警示条

### 数据管道接通路径

```
confirmIterationAnalysisOp()
  │ 已有：extractKnowledgeBaseUpdateOp() → 更新 KB
  │ 已有：detectOntologyCollisionsOp() → 碰撞检测
  │
  │ 需接通：
  │   ontologyModelingBridge.buildModelingInputFromAnalysis()
  │     → ContinuousModelingRepository.saveCandidateSnapshot()
  │     → updateSnapshotStatus("published")
  │     → ProjectModelView API 返回真实数据
  │
  └── 前端 useProjectModelView hook 自动拉取 → 图谱刷新
```
