# BuildWise 平台产品操作手册

## 1. 文档定位

本文档面向首次接触 BuildWise 的产品经理、业务负责人、技术负责人、QA 和平台管理员。  
目标是帮助读者基于当前仓库已落地实现，快速理解平台结构、业务链路、角色交互方式和标准操作路径。

说明：

- 对外产品定位以根目录 `README.md` 为准。
- 当前实现与运行方式以 `v2/README.md`、`v2/backend/README.md` 为准。
- 本文档聚焦“如何使用平台完成一轮真实交付”，不是部署手册，也不是研发规范。

## 2. 平台是什么

BuildWise 是一个把业务意图转成可执行软件交付流程的平台工作台。  
它不是单纯的聊天工具，而是把以下能力放进同一个项目空间：

- 项目与迭代管理
- 需求材料上传与分析
- 业务建模与领域建模
- 变更边界确认
- 交付物推进与评审
- 测试矩阵执行
- 发布评审与部署门禁
- 项目级知识沉淀与检索
- OpenClaw 协作执行

## 3. 平台核心对象

### 3.1 Tenant

Tenant 是租户边界。  
用户登录后可以在左侧菜单切换当前租户，不同租户下可访问的项目和权限不同。

### 3.2 Project

Project 是长期知识边界。  
一个项目会持续沉淀：

- 业务术语
- 规则
- 实体关系
- 组件与代码映射
- 决策日志
- 已知风险
- 变更模式

### 3.3 Iteration

Iteration 是项目内的一次版本推进。  
每个迭代都有自己的目标、范围、验收标准、分析结果、交付物、测试状态和发布评审结论。

### 3.4 Workspace

Workspace 是项目运行边界，不是临时聊天会话。  
每个项目会绑定一个独立 `workspacePath`，BuildWise 会把项目知识同步到：

- `workspacePath/.buildwise/workspace.json`
- `workspacePath/.buildwise/memory/`
- `workspacePath/.buildwise/shards/`
- `workspacePath/.buildwise/index/`

## 4. 典型使用角色

### 4.1 产品经理 / 业务负责人

主要操作：

- 创建项目和迭代
- 上传需求文档、原型、截图、HTML
- 查看 AI 分析结果
- 确认分析理解是否准确
- 收敛变更边界
- 审阅交付物和发布评审

### 4.2 技术负责人 / 开发负责人

主要操作：

- 检查变更边界是否完整
- 关联仓库和 workspace
- 审查模型、组件、接口和代码映射
- 评估仓库状态与远端 Git 健康
- 决定是否进入发布

### 4.3 QA

主要操作：

- 查看变更控制信息
- 执行测试矩阵
- 标记通过、失败、阻断、跳过
- 查看覆盖率和通过率
- 参与发布评审

### 4.4 平台管理员

主要操作：

- 管理平台角色与自定义角色
- 维护项目策略和全局策略
- 绑定项目成员权限
- 检查 OpenClaw 和运行时状态

## 5. 平台主要界面

## 5.1 营销首页

用于产品展示和入口跳转。  
未登录用户访问默认进入该页面。

## 5.2 登录页

当前采用手机号验证码登录。  
开发环境下验证码可由后端调试接口直接返回。

## 5.3 仪表盘

仪表盘用于查看全局概览，包括：

- 项目总览
- 进行中和已完成迭代
- 风险与近期动态
- 趋势视图

适合管理者快速判断平台当前整体状态。

## 5.4 项目工作台

这是核心页面。  
平台的大多数交付动作都在这里完成，包括：

- 选择项目
- 查看项目总览
- 创建迭代
- 进入迭代工作区
- 上传需求材料
- 推进交付物与测试

## 5.5 权限设置页

用于查看和维护权限角色、权限点和绑定关系。

## 5.6 OpenClaw 工作台

用于与 OpenClaw 协作执行任务。  
平台负责注入项目知识、策略与边界约束，Agent 负责决定会话推进顺序。

## 6. 标准业务链路

BuildWise 当前已落地的推荐业务链路如下：

1. 登录并选择租户
2. 创建或进入项目
3. 配置仓库与项目 workspace
4. 创建迭代并填写目标、范围、验收标准
5. 上传需求文档、原型、截图或 HTML
6. 查看 AI 分析结果
7. 进行人工确认和澄清
8. 确认变更边界
9. 生成、编辑和提交交付物
10. 执行测试矩阵
11. 查看发布评审
12. 满足门禁后发版或记录部署
13. 将规则、决策和知识回写到项目 workspace

## 7. 首次使用操作指南

### 7.1 登录平台

操作步骤：

1. 打开登录页。
2. 输入手机号。
3. 点击获取验证码。
4. 输入验证码并提交。
5. 登录成功后进入仪表盘。

注意事项：

- 手机号必须是 11 位大陆手机号。
- 当前手机号需要先绑定到平台成员角色，否则无法通过验证。

### 7.2 切换租户

操作位置：

- 左侧侧边栏用户菜单

操作效果：

- 切换租户后，项目列表、角色和可访问资源都会重新加载。

适用场景：

- 同一用户服务多个组织或业务空间时

### 7.3 创建项目

操作步骤：

1. 进入 `Projects` 页面。
2. 点击“新建项目”。
3. 输入项目名称与描述。
4. 提交后项目出现在左侧项目列表中。

建议做法：

- 项目名称直接使用业务系统或业务域名称。
- 项目描述写清本项目要解决的核心业务问题。

## 8. 项目层操作指南

### 8.1 查看项目总览

进入项目后，右侧总览面板可查看：

- 当前项目健康度
- 最近迭代
- 项目进度
- 模型摘要
- 业务实体、规则、关系图
- 仓库状态
- 策略和角色绑定

这部分适合在进入具体迭代前先理解项目全貌。

### 8.2 配置项目仓库

项目仓库支持三种模式：

- `external_git`
- `managed_local`
- `hybrid`

常见操作：

- 绑定远端仓库 URL
- 校验远端仓库是否可达
- 调整生产/预发是否强制要求远端 Git
- 查看远端配置、可达性和同步状态

适用建议：

- 演示或本地实验可使用 `managed_local`
- 需要受控发布时建议使用 `hybrid` 或 `external_git`

### 8.3 绑定项目 workspace

操作目的：

- 让项目具备独立知识空间
- 让 OpenClaw 和知识物化都围绕该项目展开

操作结果：

- 平台会在项目绑定路径下生成 `.buildwise/`

注意事项：

- 同一路径不能重复绑定给多个项目
- 建议使用绝对路径
- `.buildwise/` 应保留读写权限且不要纳入 Git

### 8.4 查看项目建模

项目总览中可查看：

- 业务实体卡片
- 规则映射
- 关系叙事
- 关系图谱
- 业务摘要

这些信息用于帮助业务和技术团队对齐对系统的理解，而不是只围绕单次需求讨论。

## 9. 迭代层操作指南

### 9.1 创建迭代

操作步骤：

1. 在项目总览中点击“新建迭代”。
2. 填写迭代名称、描述、版本类型。
3. 填写目标、范围内项、范围外项、验收标准。
4. 创建成功后进入该迭代。

建议做法：

- 验收标准尽量具体，因为后续测试矩阵与发布评审会依赖这些内容。

### 9.2 进入迭代工作区

迭代工作区是平台交付推进的主阵地，包含：

- 会话区
- 上传区
- 分析抽屉
- 交互编辑区
- 交付物预览
- 测试矩阵和发布评审

### 9.3 上传需求材料

支持的输入方式包括：

- 文本与说明
- 单文件上传
- 文件夹上传
- 图片
- HTML 或原型相关文件
- 二进制文件摘要

平台会根据材料类型选择不同分析策略，例如：

- 直接摘要分析
- 分块摘要分析
- 文件夹批量分析
- 无文本降级分析

### 9.4 查看分析结果

分析结果通常包括：

- 当前需求理解
- 项目识别与产品识别
- 重点发现
- 优先级问题
- 澄清问题
- 追溯映射
- 版本差异
- 风险与建议
- 发布评审草案

对于图片、HTML 和原型，平台还会提供交互编辑相关能力。

### 9.5 人工确认分析

这是迭代推进中的强制关口。

如果分析不准确：

- 标记为不准确
- 输入补充说明
- 系统继续保留待确认状态

如果分析准确：

- 补齐或确认澄清问题
- 明确变更边界
- 完成确认

注意事项：

- 在 `pendingHumanConfirmation=true` 时，发布会被阻断。

### 9.6 确认变更边界

当前平台用三类引用来收敛边界：

- `requirementRefs`
- `componentRefs`
- `codePaths`

边界的作用：

- 限定后续交付物和修改范围
- 提供 traceability 依据
- 作为测试矩阵和发布评审的输入

### 9.7 与 Agent 对话推进

在迭代会话区，用户可以直接用自然语言继续推进流程，例如：

- 补充领域规则
- 要求补齐测试
- 调整原型
- 追加发布判断依据

平台不会在前端写死固定问答树，而是把上下文、策略与边界交给 Agent 决策下一步。

### 9.8 原型和交互编辑

若上传了 HTML、截图或原型相关资产，可进行：

- 选中元素
- 提出视觉修改指令
- 执行交互修改
- 记录局部变更历史

适用场景：

- 业务方直接指出页面要调整的区域
- 产品经理快速表达交互修改意图

## 10. 交付物与评审

### 10.1 交付物草稿

平台支持交付物草稿编辑和保存。  
适用于分析报告、测试材料和其他结构化产物。

### 10.2 提交交付物

提交后平台会：

- 保存提交摘要
- 记录证据
- 在会话流里追加交付物引用消息

这样做的目的，是保证交付过程可追溯，而不是把交付物散落在会话外部。

### 10.3 交付物确认

QA、PM 或负责人可对交付物进行确认。  
若确认失败，平台会触发对应的阻断或管理员确认请求。

## 11. 测试矩阵操作指南

### 11.1 查看测试矩阵

测试矩阵由变更边界和验收标准驱动生成。  
每条用例会带有唯一 `caseId` 和执行状态。

### 11.2 更新执行状态

可更新为：

- `pending`
- `passed`
- `failed`
- `blocked`
- `skipped`

每次更新都建议填写执行人和备注。

### 11.3 查看测试统计

平台会自动汇总：

- 总用例数
- 已执行数
- 通过数
- 失败数
- 阻断数
- 覆盖率
- 通过率

这些指标会被发布评审直接引用。

## 12. 发布评审与部署

### 12.1 查看发布评审

发布评审会输出：

- `go`
- `caution`
- `block`

同时给出：

- 分数
- 阻断项
- 建议
- 风险说明

### 12.2 影响发布的常见门禁

以下情况通常会导致阻断：

- 分析尚未人工确认
- 验收标准未覆盖
- release review 决策为 `block`
- 生产要求远端 Git，但仓库未配置或不可达
- 关键测试失败或阻断

### 12.3 创建部署记录

平台支持创建：

- `staging`
- `production`

部署记录会带有：

- 项目
- 迭代
- 版本号
- 环境
- 当前状态

### 12.4 推进部署状态

部署状态可按流程推进，例如：

- `queued`
- `running`
- `success`
- `failed`

这有助于把“能不能发”和“发了之后处于什么状态”统一纳入平台。

## 13. 权限与治理操作指南

### 13.1 平台角色

平台角色用于控制全局治理能力，例如：

- 查看治理日志
- 维护平台成员
- 创建全局策略

### 13.2 项目角色

项目角色用于控制项目级读写和管理权限。  
常见参与者包括管理员、成员和查看者。

### 13.3 自定义角色

管理员可以创建自定义角色，并分配权限点。  
这样可适配不同组织对职责边界的治理要求。

### 13.4 策略与审计

平台支持：

- 项目策略
- 全局编排策略
- 执行日志
- 审计日志

适用场景：

- 强化人工确认关口
- 控制首版或跨版本流程
- 留存关键治理动作证据

## 14. OpenClaw 使用说明

### 14.1 OpenClaw 的定位

OpenClaw 在 BuildWise 中是协作执行能力，不是独立信息孤岛。  
BuildWise 负责：

- 注入项目上下文
- 传递策略约束
- 维护知识空间
- 做审计追踪

OpenClaw 负责：

- 决定澄清、边界、计划、测试、发布的推进顺序
- 基于上下文输出下一步动作建议

### 14.2 项目级知识沉淀

每个项目对应独立 workspace。  
OpenClaw 不需要每轮从头理解项目，而是可以持续利用 `.buildwise/` 中的项目知识。

### 14.3 适合通过 OpenClaw 做什么

- 继续澄清需求
- 对边界做影响评估
- 结合项目知识生成测试思路
- 在约束内推进交付对话

## 15. 知识库与回写机制

平台会把项目知识自动物化为多个文件：

- 项目摘要
- 业务术语与稳定规则
- 技术本体、组件与代码映射
- 决策、风险与变更模式
- 发布历史
- 每日汇总
- 分片和索引

它的价值不在于“多生成几份文档”，而在于：

- 让后续版本能继承上下文
- 让 Agent 有稳定知识来源
- 让团队不再每轮重新对齐业务规则

## 16. 推荐操作习惯

### 16.1 先建项目，再跑迭代

不要把一次需求临时当成独立会话。  
正确方式是先建立项目知识边界，再在项目下推进迭代。

### 16.2 验收标准要尽量提前写清

测试矩阵、发布评审和阻断判断都依赖验收标准。  
验收标准越清晰，后续自动化越稳定。

### 16.3 分析确认不要跳过

分析确认是控制错误理解扩散的关键步骤。  
如果跳过，后续交付物和测试都可能建立在错误理解上。

### 16.4 边界尽量写成可追溯引用

尽量明确到：

- 需求编号
- 组件名
- 页面名
- 代码路径

这样后续交付、测试和发布结论才有依据。

### 16.5 把重要规则沉淀到项目中

不要让关键业务规则只存在于某一轮对话里。  
应通过分析、建模和项目知识同步，把规则持续沉淀下来。

## 17. 常见问题

### 17.1 为什么分析后不能直接发版

因为平台要求“AI 理解”和“人工确认”之间必须有明确关口。  
只有在确认理解准确、边界清晰、测试和评审通过后，发布才有依据。

### 17.2 为什么需要项目级 workspace

因为平台要沉淀的是长期项目知识，而不是单轮会话结果。  
没有项目级 workspace，后续版本就无法稳定继承上下文。

### 17.3 为什么仓库远端状态会影响发布

因为 BuildWise 不是纯文档平台，而是交付平台。  
当组织要求生产必须绑定远端 Git 时，平台会把仓库健康纳入发布门禁。

### 17.4 什么情况下适合使用 OpenClaw

当需求还在收敛、边界需要持续评估、或需要围绕项目知识做连续交互推进时，就适合使用 OpenClaw。

- 租户登录与切换
- 项目和迭代管理

- 项目建模与领域建模展示
- 测试矩阵与发布评审
- 仓库治理与部署记录
- 权限治理

真实投产仍应以后端生产文档和实际环境检查为准。
