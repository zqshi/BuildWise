## 各任务实施要点

### T1 — 本体 publish 覆盖 bug 修复（done，2026-06-29，方案 B）
**产品决策**：选方案 B（candidate id 含版本序号），允许多版本候选并存，不覆盖 published，不限重做本体建模。

**交付**：
- domain 纯函数 `nextCandidateVersionNumber(snapshots, iterationId)`（`continuousModelingSupport.ts`）：解析已有快照 id 的 `-v${n}-candidate` 取 max+1；旧 id 无版本序号视为 v0 不增序号；仅计同 iterationId。向后兼容旧数据。
- `planIterationModeling` 接入：查 `listSnapshots` 算 n，生成 `snapshot-${projectId}-${iterationId}-v${n}-candidate` + version `X.Y.v${n}.candidate`。publish 后再 saveCandidate 生成 v2 不覆盖 v1 published（核心 bug 修复）。
- **T2 遗漏补**（真实投产必修）：`continuousModelingRoutes` 抽 `resolvePublishFailureHttp(reason)` 纯函数，补 `unresolved_blocking_reviews`→409+"存在未解决阻断评审，须先解决再发布"（v0.25.0 T2 加的 reason 未接 REST，原走 404 误报；现 409 正确）。snapshot_not_found/project_not_found→404，其余→409。
- **mock 修正**：`continuous-modeling.test.mjs` 两处内联 mock 补 `listSnapshots`（返回 []，planIterationModeling 现需查它算 n）。
- **测试**（`tests/ontology-candidate-versioning.test.mjs`，12 例全绿）：nextCandidateVersionNumber 6 例（空/已有 v1/最大+1/旧无序号/旧+v2 共存/跨迭代过滤）+ planIterationModeling 3 例（首版 v1/publish 后不覆盖/双候选并存，真实 Json repo）+ resolvePublishFailureHttp 3 例。全量 595 零回归（583+12），typecheck/lint/boundaries 通过。

**方案 B 对 T2 的影响**：T1 后候选 id 版本化，saveCandidate 生成新 id 不命中旧 → mock push 与真实 upsert 在 saveCandidate 路径行为一致（都是新增）。T2（mock 改 upsert）的必要性收窄至 resolveReviewTask 写回同 id 路径（resolve 用 saveCandidateSnapshot 写回原 id，mock push 会重复 push，真实 upsert 覆盖）。T2 起步须重新评估范围。

### T2 — mock/真实 repo 语义一致（done，2026-06-29）
**交付**：`createInMemoryModelingRepo.saveCandidateSnapshot` 由 push 改 upsert（对齐 JsonContinuousModelingRepository，同 id 覆盖）。
**发现并修复 mock 掩盖的真实行为 bug**：resolveReviewTask 写回同 id 快照时，mock push 下第二次 resolve 读到第一次 push 的旧快照（review-b 的 resolved 未写到 review-a 已 resolved 的那份）→ 多次解决累积 resolved 被掩盖、publish 误阻断。mock 改 upsert 后写回覆盖、resolved 累积正确。
**测试**（`tests/ontology-resolve-persistence.test.mjs`，3 例全绿）：两次解决累积 resolved + 不重复 push（mock 一致性契约）+ publish 放行 + workspaceService 层累积。全量 598 零回归（595+3），typecheck/lint/boundaries 通过。既有用 createInMemoryModelingRepo 的测试（gate-service/publish-blocking/workspace）零破坏——证实 T1 版本化 id 已让 saveCandidate 路径不受影响，T2 仅 resolve 写回路径受益。

### T4 — typed table tenant scope（done，2026-06-29，已核实无风险，不改代码）
**核实结论**：v0.23.0 判断成立，无需强加 DB scope。
- `listIterations/findIteration/listMessages`：HTTP 入口均经 `ensureIterationAccess`/`ensureProjectAccess`（应用层 tenantAccess）校验后才传 id 到 repo——外部可控 iterationId/projectId 先校验归属当前租户，无不经校验直传的路径。
- `listAuditLogs(limit)`：`/governance/audit-logs` 是全局治理路由（不在 `/projects/:id/` 下），`requireAdmin` 限平台超管；`audit_logs` 表无 tenant_id 列（payload blob），AuditLog 是平台级审计。平台超管看全局审计日志是合理设计，非跨租户串。
**决策**：不为不存在的风险强加可选 tenantId scope（强加反增维护面无收益）。记入约束供后续若 audit 需租户隔离时评估。
