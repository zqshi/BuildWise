## 版本目标

本版本双线交付：

1. **产品交互**：解决用户反馈"需求池完成版本归属后，需求仍堆在需求池、归属后无移入版本视觉闭环、多版本不便管理"。后端能力已齐全（`BacklogItem.iterationId` + `assignBacklogItemsToIterationOp`），问题在前端默认平铺视图 + 下拉归属单薄。改为默认版本分组 + HTML5 原生拖拽归属（零新依赖，后端零改动）。
2. **门禁加固**：全面质量检测发现"门禁全绿"是表象——契约测试子进程模式从未跑通、契约被 verify:prod-readiness glob 跳过、Prompt 检测器对动态 userPrompt 失明。三道"绿但失效"门禁须真正生效，verify:all 方算真绿，否则 v0.13.0 不能归档。

## 关键技术决策表

| 决策 | 理由 |
|------|------|
| 契约路径修复用 DRY 复用 versionedPath 而非补两处短路 | 子进程模式内联了路径改写没复用 versionedPath 是根因；复用消除双模式不一致源头，非头痛医头 |
| ALLOW_SEED_DATA_BOOTSTRAP=true 只在 fixture 子进程 env 设 | .env 默认 false（避免 dev 覆盖已有 workspace.db）；fixture 是空 db 本就该 seed data.json，显式开启不污染 dev 环境 |
| test:contract 纳入 verify:prod-readiness 而非改 glob 为 *.mjs | contract.mjs 是顶层 await 自包含脚本（非 node --test 格式，用 exitCode=1 表失败），塞进 node --test 行为不可控；显式 && npm run test:contract 清晰 |
| 双契约门禁互补 | prod-readiness 跑子进程契约（spawn 真实 server），prod-release 跑 in-process 契约（app.inject），双模式都验证契约有效性 |
| Prompt 检测器只扫字面量 userPrompt | 函数动态构造（buildXxxUserPrompt）检测器扫不到函数内部，靠手工修 + code review 把关；检测器末尾 log 此局限不做 silent cap |
| 检测器 extractUserPromptValue 按字面量类型截取 | 初版用 NEXT_FIELD_PATTERN + 600 字符截取，userPrompt 是对象末字段时含后续代码误报（10 处）；精准截取后降到 4 真实违规 |
| T1.6 取消归属仅 planned 回退 open | done 项取消归属保持 done（已不在版本内但完成状态不变），避免误改工作进度；语义正确 |

## 对后续版本的约束

- **verify:prod-readiness 现含 test:contract**：日常门禁跑子进程契约，路由/逻辑改动若破坏契约 CI 会捕获。此前子进程模式盲区已补上。
- **Prompt 门禁现扫 src/ 动态 userPrompt**：新增/修改 application 层 userPrompt 赋值时，禁止拼入 JSON schema 字段名（schema 走 expectedOutput），否则 check:prompts 报红。函数动态构造的 userPrompt 需 code review 把关（检测器扫不到函数内部）。
- **契约子进程模式依赖三处修复**：后续若 test:contract 再坏，先查 contractHarness 的 versionedPath 短路、ALLOW_SEED_DATA_BOOTSTRAP env、httpTestClient.waitForHealth 轮询。
- **归档前置**：v0.13.0 后归档任何版本须 verify:all 真绿（含子进程契约 + in-process 契约 + prompt 动态扫描），不再接受 in-process 单模式"假绿"。
