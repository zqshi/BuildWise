# v0.25.0 Snapshot — 本体评审解决流程（评审门禁升级为发布前须解决阻断评审）

> 状态: 已归档（2026-06-29）
> 起始 commit: 21bb1e8 (2026-06-28)
> 上一版本: [v0.24.0](v0.24.0-snapshot.md)

## 版本目标
v0.24.0 激活本体发布门禁，但评审门禁受限于 ReviewTask 无解决路径——"候选态阻断+发布即认可"（published 不查历史 blocking）。本版建本体评审解决流程：用户确认术语/规则后标记评审已解决，使 candidate→publish 前须解决阻断评审。完成后评审门禁从"发布即认可"升级为"发布前须解决阻断评审"，让本体评审真正独立阻断，夯实核心价值（活的知识链条的本体质量门禁）。

## 交付内容摘要
- **T1 评审解决流程**（done，commit b2cb913/22f9a16/fb24ba4）：`resolveReviewTaskOp` 纯函数（domain/continuousModeling/resolveReviewTask.ts，与 ontologyReleaseGate.ts 同构）标候选快照评审 `resolved=true`；设计约束——仅 candidate 可解决（published=发布即认可/superseded=已让位）、幂等（重复标记仍 ok）、保留历史（标 resolved 不移除）。`ReviewTask` 加可选 `resolved?: boolean`。`ContinuousModelingService`/`ContinuousModelingWorkspaceService` 加 resolveReviewTask，复用 `saveCandidateSnapshot` upsert 写回（零 schema 迁移）。9 测试。
- **T2 评审门禁语义升级**（done）：`getUnresolvedBlockingReviews` domain 纯函数（reviewTaskStatus.ts，统一未解决阻断评审判定）；`publishSnapshot` 前置检查——candidate 有未解决 blocking → `unresolved_blocking_reviews` 阻断（状态更新前 return，快照保持 candidate），无 blocking 放行维持原行为；`OntologyGateService` filter 改用之，已解决评审不计入交付阻断。`evaluateOntologyReleaseGate` 纯函数未改（输入语义由调用方保证）。8 测试。
- **既有测试修正 3 例**（continuous-modeling-workspace）：T2 后 `saveCandidate→publish` 假设失效（2 失败 + 1 假通过 `does not duplicate`），改为直接构造无阻断评审快照聚焦 diff/KB 回写/去重意图，恢复测试有效性。
- **T3 归档验证**：verify:all 全绿（后端 583 含新增 17 / 前端 227 fail 0 / 契约 passed / prod-release alerts 空），6 项质检全过，分层入库。

## 关键技术决策表
| 决策 | 选择 | 理由 |
|---|---|---|
| 评审解决语义 | 标 resolved=true 不移除评审 | 保留活的知识链条历史可追溯；可选字段向后兼容旧 JSON |
| 可解决阶段 | 仅 candidate | published=发布即认可（v0.24.0 约束）/superseded=已让位，无需再解决 |
| 幂等 | 已 resolved 重复标记仍 ok | 不阻断用户确认流程，避免重复操作报错 |
| 持久化 | 复用 saveCandidateSnapshot upsert 写回 | 零 schema 迁移（reviewTasks 是 JSON 数组），符合 v0.24.0 delegate 注入不改持久化决策 |
| 未解决计量 | 抽 getUnresolvedBlockingReviews domain 纯函数 | publish 前置与交付门禁共用，避免 blocking&&!resolved 多处重复 |
| publish 阻断点 | 状态更新前 return | 快照保持 candidate，T1 resolve 流程可继续在其上操作 |
| onAnalysisConfirmed 回调 | 零改动 | 自动 publish 在有 blocking 时被门禁阻断停 candidate（回调不看返回值自然停），无 blocking 正常 publish；与 v0.24.0 发布即认可正交协同 |

## 遗留问题
- `createInMemoryModelingRepo.saveCandidateSnapshot` 是 push，真实 `JsonContinuousModelingRepository` 是 upsert（同 id 覆盖）；既有 diff 测试依赖 mock push 掩盖、真实 repo 下本会失败。→ v0.26.0 T2
- 同 iteration publish 后 saveCandidate 同 id 覆盖 published 快照（candidate id 固定 `snapshot-${projectId}-${iterationId}-candidate`）需产品判断（禁止/候选 id 含版本序号）。→ v0.26.0 T1
- `onAnalysisConfirmed→自动 publish→阻断停 candidate` 集成链无测试守护（app.ts 装配层）。→ v0.26.0 T3
- listIterations 等 tenant scope / assistant_messages 核实 / useAuthController hook 单测 → v0.26.0 统一收口（T4/T5/T6）

## 对后续版本的约束
- 评审门禁独立阻断：candidate→publish 前须解决所有阻断评审，全部解决后放行；published 后门禁不因历史 blocking 误阻（发布即认可保留）
- v0.24.0 发布即认可 published 路径不回退，T2 仅 publish 前置加阻断，两者正交
- onAnalysisConfirmed 自动 publish 在有 blocking 时自然停 candidate——分析确认后本体快照不再自动 publish（需用户先解决评审），是预期行为变化
