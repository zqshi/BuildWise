## T1 探路结论（done 2026-06-28）

### 1. 实际表数与分类（核实「16 表」严重低估）
真实 ~23 张业务表 + 2 系统表（schema_migrations / revoked_tokens），分三类：
- **有 tenant_id 列（2）**：`projects`（002_fix_orphan_tenant 加，`TEXT NOT NULL DEFAULT 'default'`）、`assistant_messages`（008，NOT NULL + 索引，已正确使用）
- **无 tenant_id 列，租户靠 project_id 链式关联（~16）**：iterations/messages/audit_logs/attachment_uploads/attachment_upload_files/attachment_file_chunks/attachment_ingest_jobs/attachment_analysis_jobs/attachment_analysis_batches/attachment_reports/attachment_report_sections/analysis_jobs/report_indexes/report_sections/backlog_items/knowledge_entries/knowledge_graph_cache/experience_policies/experience_extractions
- **JSON blob 无列概念（1）**：`workspace_collections`（20 个领域集合各整序列化为单行 payload blob）

### 2. 存储是双轨制（难点一坐实）
- **workspace_collections（JSON 文档存储）**：20 个领域集合（projects/iterations/.../platformRoleBindings）整序列化进 payload，`readStore()`/`writeStore()` 全量读写
- **typed tables（关系型表）**：projects/iterations/messages/audit_logs 有真实列，`syncTypedTables()` 从 JSON 同步
- **双写**：`writeStore()` 写 JSON blob 同时 `syncTypedTables()` 同步关系型表，`BEGIN IMMEDIATE TRANSACTION` 保证原子；createProject/updateProject/createIteration 等方法也双写（既 insertProject 关系表又 writeCollection JSON）

### 3. 核心 bug：projects.tenant_id 列存在但从未被写入（已坐实）
- 002 给 projects 加了 `tenant_id TEXT NOT NULL DEFAULT 'default'` 列
- 但 `syncTypedTables` 的 projects upsert（`sqliteWorkspaceCore.ts:407-409`）只写 `(id,name,description,status,last_updated,payload)`，**不写 tenant_id，ON CONFLICT 也不更新**
- grep 全 sqlite 层，projects.tenant_id 零写入点（仅 assistant_messages 有自己的写入）
- **后果**：projects.tenant_id 永远 = `'default'`（建列默认值）

### 4. 唯一 SQL 层 tenant 过滤范例已失效（已坐实）
- `searchKnowledgeAcrossProjects`（`sqliteWorkspaceExperience.ts:163`）：`WHERE (p.tenant_id = ? OR p.tenant_id IS NULL)` JOIN projects
- 因 projects.tenant_id 永远 `'default'`，传非 `'default'` tenantId 时永不匹配 + NOT NULL 不匹配 → **跨租户知识搜索返回空（真 bug）**
- 这是全仓唯一在 SQL 层做 tenant 过滤的查询，本应是硬隔离范例，却因列未同步而失效

### 5. 关系型表查询现状（决定 T3 插入点）
全部不带 tenant scope，100% 靠应用层 tenantAccess（v0.22.0）内存过滤：
- `listProjects`（:269）`SELECT payload FROM projects` 全表扫
- `findProject`（:278）`WHERE id`、`listIterations`/`findIteration`（:285/294）`WHERE project_id` 或 `id`
- `listMessages`（:310）`WHERE iteration_id`、`listAuditLogs`（:320）`ORDER BY id DESC LIMIT` 全表扫
- 其余 snapshot/transitions/deployments/shares/bindings 等走 `readCollection`(JSON) + `.filter()` 内存过滤

### 6. 两难点坐实结论
- **难点一（workspace_collections 双写）真实但可控**：JSON blob 路径无法 SQL 过滤，但当前查询多走 readCollection+内存 filter（应用层 tenantAccess 已覆盖）。双写一致性靠事务原子保证，不是隔离漏洞点。真正隔离漏洞在关系型 typed table 查询（无 tenant scope）。
- **难点二（系统巡检 tenant-agnostic）真实**：experience scan 的 searchKnowledgeAcrossProjects 是唯一跨 project 查询，已带 tenantId 参数（系统巡检入口设计正确），但因 bug 3 失效。无其他无 tenant 全表扫描的系统任务（fullCycleJobOps/analysisService 查询都带 iterationId/projectId 间接 scope）。

### 7. 硬隔离策略选定 → 方案重塑
backlog「16 表加 tenant_id 列 + 双写一致性」**措辞误导，不是真实方案**。真实可行方案 = **修 bug + 扩展 JOIN 过滤范式**：
1. **修 syncTypedTables 同步 projects.tenant_id**（关键 bug 修复，T2 核心）—— projects upsert SQL + extractRow 加 tenant_id 写入，让列有真实数据
2. **给关系型 typed table 查询加 tenant scope**（T3 核心）—— listProjects/findProject/listIterations/findIteration/listMessages/listAuditLogs 加 tenantId 参数，WHERE/JOIN projects.tenant_id 过滤
3. **扩展现有 searchKnowledgeAcrossProjects 范式**到其他跨表查询（JOIN projects WHERE p.tenant_id）
4. **真超管旁路**：repository 层 tenant 参数，应用层 isPlatformOwner（v0.22.0）场景不传 tenant 或传特殊标记旁路
5. **workspace_collections JSON 路径**：保持应用层 tenantAccess 覆盖，不在 DB 层强求（blob 无法 SQL 过滤，硬隔离落点在 typed table）
- 不用给 23 表全加 tenant_id 列（SQLite 无 RLS，且大部分表是 payload blob / JSON 集合，加列无数据）
