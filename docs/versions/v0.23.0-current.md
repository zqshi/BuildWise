### T1 探路 checklist（产出探路结论，定 T2/T3 方向）
- **枚举所有持久化表**：grep sqlite schema 建表语句（`CREATE TABLE` / `sqliteWorkspaceCore.ts` / `schema_migrations/`），列全表清单
- **核实「16 表」**：backlog 写「16 表」是 v0.19 时期老说法，**待核实实际表数**，逐表标注 tenant_id 现状（已有 / 缺失 / 仅部分行有）
- **硬隔离策略权衡**（SQLite 无 RLS，靠查询层 scope + NOT NULL + 索引）：
  - 方案 A：repository 层 scope filter 强制 tenant 条件（每查询必带 tenant，无 tenant 的全表查询拒绝/报错）
  - 方案 B：DB 层 NOT NULL + 索引（防 NULL 漏写，但不防跨租户串查）
  - 方案 C：双管齐下（A 防串查 + B 防 NULL 漏）—— 倾向方向，待探路确认
- **owner 语义衔接**（关键）：v0.22.0 真超管 platformRoleBinding 跨租户 admin，DB scope 层须有显式旁路，否则硬隔离反拦真超管。探路时定位 scope filter 在哪一层加旁路最干净
- **已知难点核实**（backlog 技术债，逐条坐实是否真实）：
  - `workspace_collections` JSON blob 双写一致性（核实表名是否存在 + blob 内实体如何绑 tenant）
  - 系统巡检（experience scan / fullCycleJobOps / analysisService 全表扫描）tenant-agnostic 旁路（核实哪些查询无 tenant 条件属系统任务，需旁路而非误拦）
- **TDD 起点**（探路后定具体 Red）：方向是无 tenant 条件查询应拒绝/限定 → Green（repository scope filter）→ 契约验证不破坏 dev/契约/真超管跨租户

## 对后续版本的约束
- DB 硬隔离后，tenantAccess 应用级判定（v0.22.0）保留作快路径，DB 层兜底，两层不互斥
- 16 表 tenant_id 一旦硬隔离，新增表必须带 tenant_id 列（schema 纪律）
- 真超管跨租户访问须 DB scope 层显式旁路，不可依赖应用层漏判
