## 版本目标

v0.17.0「堵数据串」让前端 `fetchJSON` 统一注入 `x-tenant-id` header 后，暴露 `GET /projects` 在「前端 tenantId 与后端租户成员状态不同步」时返回 403、前端报「项目数据加载失败」阻断用户。本版本止血+治本：后端列表接口放宽 tenantId 门禁为空列表降级；前端注入 tenantId 前过滤失效值并在租户失效时主动同步 session。

## 版本验证标准

1. 用户被移出租户 / tenantId 残留后，刷新页面不再报「项目数据加载失败 403」，而是看到空项目列表（可引导重新登录/切租户）
2. 既有正常多租户切换 / 成员可见性 / 跨租户隔离契约不回归
3. `verify:all` 全绿

## 版本范围

**做什么:**
- T1 后端 `handleListProjects` 去 tenantId 前置 403 门禁 → `listProjectsForUser` 过滤降级；更新 `invalidTenantSelection` 契约（403→200 空列表）
- T2 前端 `fetchJSON` tenantId 失效感知：注入前用 `resolveCurrentTenantId` 过滤 + 空列表时主动刷 `/auth/session` 同步租户状态

**不做什么:**
- `getTenantAccessContext` projectId=-1 fallback 修复 → 缺陷 A 核实**不可达**（`upsertProjectRoleBinding` 无路由入口，纯 project binding 用户走不到），不动
- DB 层 16 表 tenant_id 硬隔离 + owner 分支收敛 → 后续迭代（backlog P1）
- `handleCreateProject` 的 `getTenantAccess` 403 → **保留**（防伪造 tenantId 创建到别人租户，是正确安全行为）

## P1 规划（backlog 多租户硬隔离，调研于 2026-06-27）

backlog P1 含两块，调研后建议拆分处置：

### T3 — owner 分支收敛（并入 v0.18.0，P1，pending）

**缺陷**：`workspaceRouteUtils.ts:61,108` 的 `if(role==="owner")` 分支——超管（authRole=owner）访问**有租户项目**时，分支内仅在 `!tenantId`（无租户）时短路放行；有租户则 fall through 到 `getProjectAccess(userId)`，而超管 userId 不在 tenant member/project binding → `resolveTenantRole=null` → `canRead=false` → **超管被 403**。即超管只能访问无租户项目，逻辑断裂。

**收敛方案（待设计决策）**：
- 方案A（简单）：owner 分支统一返回放行 context（无论有无租户），超管访问全部项目。权限大但语义清晰。
- 方案B（收敛）：移除 ensure*Access 的 owner 特殊分支，让超管也走 `getProjectAccess`，但 `resolveTenantRole` 对超管 userId 增加旁路（authRole=owner 时 tenantRole=admin）。
- 需产品确认：超管是否应跨租户访问所有项目。

**TDD**：Red「超管 GET 有租户项目 /iterations 期望 200 当前 403」→ Green 收敛 → 契约验证不回归。

### v0.19.0 — DB 层 16+ 表 tenant_id 硬隔离（拆独立版本，大工程）

**不建议并入 v0.18.0**：涉及 001-008 迁移的 20+ 张业务表加 tenant_id（新 migration 009）+ repository 所有查询加 tenant 过滤 + `workspace_collections` JSON blob 与 typed 表双写一致性（`sqliteWorkspaceCore.ts:405` syncTypedTables）+ 系统巡检 tenant-agnostic 旁路（`analysisService.ts:111` restoreFromDb 全表扫描 / fullCycleJobOps）。高风险，需独立版本周期 + 迁移测试 + 双写一致性验证。v0.18.0 只做 P0 止血（T1/T2）+ T3 逻辑收敛，DB 硬隔离留 v0.19.0。
