## 各任务实施要点

### T1 — A→B 回写冗余评估 + 处置
**起步**：核查 `continuousModelingWorkspaceService.publishSnapshot` 的 `snapshotToKbPatch`（:79/:194）把快照内容回写 ProjectKnowledgeBase 的真实消费链——
- B 套 KB（ontologyTerms/stableRules/componentInventory）被谁消费？变更影响/门禁/代码回流是否真读 KB 而非快照？
- A 套快照 publish 后回写 KB 是否冗余（双写绕圈）？还是 KB 是快照的物化视图需同步？
- 决策：若 KB 是独立数据源被多处消费→保留双写但明确语义；若 KB 仅是快照派生→收敛为 KB 视图层（读时从快照派生，不写回）。

需产品判断本体（A 套快照）与知识库（B 套 KB）的单一数据源归属。TDD Red 先行（若收敛，验证 KB 读时从快照派生）。

### T2 — per-prefix 超限文件拆分
15 个超限文件中核心高风险（>400 行或职责膨胀）优先拆：
- `coreOps.ts` 431 行 / `ontologyService.ts` 455 行 / `analysisOps.ts` 530 行 / `synthesisTaskOps.ts` 400 行
- 按 v0.17.0 T3 策略：拆出独立子域函数文件，保持接口不变，TDD 保护零回归。
- 伪超限（接近软限但职责单一）不拆。

### T3 — 前端 Props Drilling 残留评估
v0.17.0 T5 已迁 7 个 Context 承载 ProjectsWorkspace props。核查：
- ProjectsWorkspace 当前 props 数量是否仍偏高？是否有残留可迁 Context？
- 评估结论：已收敛标注 / 残留项列出转后续。
