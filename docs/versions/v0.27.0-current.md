## 各任务实施要点

### T1 — A→B 回写冗余评估 + 处置
**起步**：核查 `continuousModelingWorkspaceService.publishSnapshot` 的 `snapshotToKbPatch`（:79/:194）把快照内容回写 ProjectKnowledgeBase 的真实消费链——
- B 套 KB（ontologyTerms/stableRules/componentInventory）被谁消费？变更影响/门禁/代码回流是否真读 KB 而非快照？
- A 套快照 publish 后回写 KB 是否冗余（双写绕圈）？还是 KB 是快照的物化视图需同步？
- 决策：若 KB 是独立数据源被多处消费→保留双写但明确语义；若 KB 仅是快照派生→收敛为 KB 视图层（读时从快照派生，不写回）。

需产品判断本体（A 套快照）与知识库（B 套 KB）的单一数据源归属。TDD Red 先行（若收敛，验证 KB 读时从快照派生）。

**实施结论（commit 412daeb）**：调研推翻"回写空转"初判——回写有真实功能（HTTP `saveCandidate` 入口让前端直传本体项，publish 时沉淀回 KB），但绕过正名链（`extractKnowledgeBaseUpdateOp` 的碰撞检测/增量统计/审计）是数据源单一性真问题。直接复用 `extractKnowledgeBaseUpdateOp` 不可行（强耦合分析报告追溯结构，快照 rules/entities 无法映射）。落地为"改造为正名规范"：`snapshotToKbPatch` 增强 key trim 归一（修 KB 项含空白时重复沉淀 bug）+ 返回增量统计 + `publishSnapshot` 写审计日志 `ontology.snapshot-merged`。保留合并功能，现有回写测试不破坏。TDD 2 例 + 全量 603 单测 + 契约通过。
