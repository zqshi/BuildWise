## 版本目标

v0.13.0 流畅性审查暴露**架构级流畅性短板**（非局部 bug）：fullCycle 全管道同步阻塞单 HTTP（5-6 次 LLM/agent，可达 30min+，网关默认 60s 超时即断连，前端拿到断连错误而非管道状态）+ 分析 Job 内存态进程重启丢 running 任务（前端轮询空等 25min 超时）。本版本复用 v0.8.0 `codeRewriteJobOps` 异步 Job 状态机模式，改造 fullCycle 异步化 + 两类内存态 Job 重启恢复，消除「幽灵 running」。

## 版本验证标准

1. fullCycle 触发后立即返回 jobId，HTTP 不阻塞；前端轮询拿管道进度与最终结果
2. 进程重启后，重启前 running 的 fullCycle/分析 Job 能被识别并恢复或标记失败，不卡死
3. fullCycle 步骤失败时已写盘文件回滚，不产生「半改写」状态（不造假）
4. verify:all 真绿（含子进程契约 + in-process 契约 + prompt 动态扫描）

## 关键技术决策表

| 决策 | 理由 |
|------|------|
| 分析 Job 幽灵 running 标 failed 而非重新入队 | 不偷偷重跑消耗 LLM，给用户控制权，符合「不造假」；复用 `markFailedAnalysisOp` 失败路径 + `retryLatestFailedAttachmentAnalysisJob` 一键重试 |
| fullCycle resumable checkpoint 标 interrupted 而非自动续跑 | 后续 step 含改代码/推远程副作用，重启场景自动续跑风险高；用户手动触发 `handleResumeFullCycle`，`runIterationFullCycleOp` 读 checkpoint + `executeStepLoop` 跳过已完成 step |
| 两类 Job 恢复机制各自独立不共享 | 分析 Job=队列+worker+超时 reconcile，fullCycle Job=单 job fire-and-forget，语义不同不宜强行共享 |
| 中断查询端点复用 buildInterruptedSummary | scan 与 getInterruptedFullCycle 共享判定/摘要纯函数，DRY |
| 前端横幅引导输入「继续全流程」续跑而非独立按钮桥接 deps | ChatContext 不暴露 action dispatch，续跑已通过聊天输入触发（chatActions.ts 续跑分支）；横幅自包含 fetch 零 deps 桥接，最小回归风险 |
| T11 步骤失败回滚改前内容而非暂存区提交 | 直接回滚已写盘文件，遵循「不造假」禁止半改写透传；比暂存区提交更轻 |
