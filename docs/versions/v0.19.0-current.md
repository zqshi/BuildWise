## 版本目标
用户指出两个根本性架构问题（v0.18.0 调研坐实）：①迭代对话是阶段驱动的确定性编排，不识别用户「询问」意图，每次对话无条件合成交付物+推进阶段——「运行态（对话）与执行态（产交付物/推进）未分离」；②fullCycle 全流程的编码步骤（frontend-rewrite/backend-rewrite）走 `llmCodeRewriteOps`（LLM 同步生成），未接真实 codingAgent，核心价值闭环（编码改动回流本体）在生产流程断裂。本版本根治：迭代对话接入意图识别分离运行/执行态；fullCycle 编码步骤改接真实 codingAgent（引入 OpenHands adapter）。

## 版本验证标准
1. 用户在迭代对话「询问逻辑」时，系统纯对话回答，不产交付物、不推进阶段；「推进/生成」意图才触发交付物合成
2. fullCycle 的 frontend-rewrite/backend-rewrite 步骤真实调用 codingAgent（adapter.start→getEvents→close），LLM 仅作 codingAgent 不可用时降级
3. 编码 agent 改动真实回流本体（codePaths 来自真实 agent diff 事件）
4. verify:all 全绿

## 各任务实施要点

### T1 — 迭代对话意图识别 + 运行/执行态分离

**现状缺陷**：`orchestrateCoachMessage`（stageOrchestrator.ts）阶段驱动：`evaluateCurrentStageGate`→`getStageAgent(currentStage)`按阶段选 Agent（不识别意图）→LLM 回复→`attemptArtifactSynthesis` 无条件合成交付物→`evaluateAndAdvanceStage` 自动推进。用户「询问逻辑」被当推进输入，仍产交付物。全局 `assistantChatOps.classifyIntent` 有意图识别（5类），迭代对话无——割裂。

**方案**：`coachIterationConversationOp` 在 `orchestrateCoachMessage` 前加意图分类（询问/推进/澄清/生成）。询问类走纯对话（AgentRunner 单次回复，不触发 attemptArtifactSynthesis + 不推进阶段）；推进/生成类才走现有阶段编排+交付物合成。复用 `assistantChatOps` 的 classifyIntent 模式下沉为共享纯函数。

**TDD**：Red「用户询问类消息不产交付物（committedArtifactTitles 为空）+ 不推进 activeStage」→ Green 意图分支 → 契约验证推进类不回归。

### T2 — OpenHands adapter 实现 + 注册

**端口**：`CodingAgentAdapter`（domain/shared/codingAgent.ts）— start(context)/getStatus/getEvents/cancel/close。对称现有 `ClaudeCodeCliAdapter`。`CodingTaskContext`（repoPath/instruction/boundaryCodePaths/role/acceptanceCriteria/maxFiles）。

**调研结论（2026-06-27 subagent）**：OpenHands 已拆分为 agent-server（FastAPI REST + WebSocket 常驻进程）+ Python SDK。**接入方式选 HTTP REST API**（非 Python SDK，避免 TS 后端嵌 Python runtime；非 OpenAI 兼容网关，拿不到结构化 tool_use/tool_result/diff 事件）。
- **start**：`POST /conversations`（workspace.working_dir=repoPath，initial_message=instruction，agent.llm 内联 base_url/api_key 从 .env 读）→ `POST /conversations/{id}/run` → 返回 sessionId
- **getStatus**：`GET /conversations/{id}` 映射 execution_status（RUNNING→running, FINISHED→completed, ERROR/STUCK→failed；无 cancelled 枚举，cancel 后本地标记）
- **getEvents**：`GET /events/search?timestamp__gte=since` → ActionEvent→tool_use, ObservationEvent→tool_result, MessageEvent→text, AgentErrorEvent→error；diff changedPaths 用 `GET /git/diff` 补偿（无原生 diff 事件）
- **cancel**：`POST /interrupt` + 本地 cancelled 标记
- **close**：清理本 adapter 会话资源（不杀 agent-server，多会话共享）
- **GLM 兼容**：✅ LLM 类 base_url/api_key 原生支持 LiteLLM，智谱 GLM OpenAI 兼容接口可直接接入，符合模型约束

**三大风险**：
1. **常驻服务运维**（最大）：agent-server Docker 常驻，需 BuildWise 引入生命周期管理 + `OPENHANDS_BASE_URL` 配置 + 健康检查 `GET /api/alive`。与 CLI 子进程模式不对称，部署文档/docker-compose 需调整。
2. **boundaryCodePaths 非原生**：adapter 层 prompt 声明边界 + git diff 后置校验实现（建议提到共享 utils，ClaudeCodeCli/OpenHands 两 adapter 复用）。
3. **diff 事件无原生类型**：从 ActionEvent(FileEditAction.path) 或 git_router 解析 changedPaths，有遗漏风险，需测试覆盖。

**部署决策待用户确认**：常驻 agent-server 是否接受（影响 T2 实施前是否先做部署拓扑）。

### T3 — fullCycle 编码步骤接真实 codingAgent

**现状缺陷**：`fullCycleSteps.ts:254-255` frontend-rewrite/backend-rewrite → `executeStepRewrite` → `rewriteCodeInBoundary`（fullCycleSteps.ts:167）→ `llmCodeRewriteOps.rewriteCodeInBoundaryOp`（LLM 同步生成）。真实 codingAgent（`agentCodeRewriteOps`，调 adapter）只在 `code-rewrite` 单独入口（handleCodeRewrite 非 dryRun）用，fullCycle 没接。

**方案**：fullCycle 的 rewrite 步骤改用 `agentCodeRewriteOps`（真实 codingAgent 会话式：start→轮询 getEvents→diff 事件回流 codePaths→close+事后边界校验）。`llmCodeRewriteOps` 降级为 codingAgent 不可用（无 registry/adapter）时的 fallback。需处理 fullCycle 步骤从同步改异步轮询（参照 codeRewriteJobOps 的 job 模式）。

**TDD**：Red「fullCycle rewrite 步骤调用 agentCodeRewriteOps 而非 llmCodeRewriteOps」+「编码改动回流 codePaths 来自 agent diff 事件」。
