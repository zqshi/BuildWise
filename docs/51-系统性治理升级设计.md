# 系统性治理升级设计

## 目的

定义 BuildWise 从“可运行的项目工作台”升级到“可持续治理、可受控投产、可长期沉淀知识的平台”的系统性收口方案。

## 范围

本文档负责：

- 当前治理缺口识别
- 目标状态定义
- 技术与工程治理工作流
- 分阶段升级路径
- 风险、验证与回滚策略

本文档不负责：

- 单个功能点的实现方案细节
- 逐条接口定义
- 运维执行手册

## 关键结论

1. BuildWise 的治理升级不能只做技术重构，必须同时收口产品模型、运行时、测试门禁、知识物化和文档体系。
2. 当前最关键的治理对象是 `Project workspace`、`Change Control`、`Release Gate`、`Knowledge Materialization` 和 `DDD Boundary`。
3. 升级优先级应按“正确性、可追溯、可发布、可沉淀、可演进”排序。
4. 任何升级都必须遵守“不侵入 OpenClaw 内核、只在 BuildWise 侧收口”的原则。

## 1. 当前问题画像

虽然 BuildWise 已具备可演示和可运行的主能力，但从理想状态看，仍存在以下系统性风险：

### 1.1 产品事实与技术事实之间仍有缝隙

表现为：

- 一部分执行版文档过于概括，无法作为真实设计基线
- 模型、架构、治理和追溯之间的联动关系表达不够清楚

### 1.2 存量大文件与职责耦合仍然明显

表现为：

- 前端工作台与交互面板仍存在超长文件
- 某些应用编排能力易再次向“大服务”回流

### 1.3 追溯和发布门禁仍需要进一步结构化

表现为：

- requirement/component/code 的三向边界虽然已有实现，但文档和门禁口径仍需完全固化
- 发布评审对追溯覆盖率的解释需要进一步标准化

### 1.4 运行时可观测性与生产准备度需要持续强化

表现为：

- 本地与生产语义仍需严格区分
- 部分验证链条依赖环境条件，失败时需要更明确的诊断口径

## 2. 目标状态

理想状态下，BuildWise 应具备以下特征：

### 2.1 产品层

- 围绕 `Tenant -> Project -> Iteration -> Knowledge` 形成稳定业务模型
- 业务人员能持续参与边界确认与版本决策
- 项目知识跨迭代持续积累

### 2.2 技术层

- 前后端严格遵循 DDD 分层
- 关键对象有统一模型
- 追溯链贯通需求、测试、代码和发布

### 2.3 工程层

- 所有核心链路都有自动化验证
- 所有关键行为变化都有文档与测试同步
- 超限文件持续递减而不是继续增加

### 2.4 运行层

- `/health`、`/ready`、`/status`、`/metrics` 语义清晰
- 生产门禁命令可重复执行
- 故障诊断可以直接定位到依赖、配置、存储或外部运行时

## 3. 升级原则

1. 不重做主产品航道
2. 不侵入 OpenClaw 内核
3. 先收口模型和边界，再扩展能力
4. 先让主链可验证，再追求功能丰富度
5. 每次升级必须同步收口文档、脚本和测试

## 4. 升级工作流划分

系统性治理升级应拆成五个工作流并行推进。

### 4.1 模型收口工作流

目标：

- 统一 Project / Iteration / Change Control / KnowledgeBase / ReleaseReview 的职责边界

产出：

- 执行版模型文档
- 契约测试同步
- API 输出结构一致

### 4.2 架构收口工作流

目标：

- 防止逻辑再次堆回巨型服务或巨型页面

产出：

- 分层守卫
- 文件拆分计划
- 上下文边界清单

### 4.3 追溯与门禁收口工作流

目标：

- 让 requirement/component/code/test/review 之间形成结构化链路

产出：

- 追溯模型文档
- 发布评审规则
- 测试覆盖指标

### 4.4 运行时收口工作流

目标：

- 提升启动、健康检查、鉴权、配置与运行时诊断的一致性

产出：

- 生产文档
- readiness 校验
- runtime status 统一口径

### 4.5 文档与治理收口工作流

目标：

- 让设计、实现、测试和门禁共享一套真实基线

产出：

- 执行版文档重构
- 文档索引
- 例外清单与治理声明

## 5. 理想技术方案设计

### 5.1 项目级 workspace 方案

Project 是长期边界，因此技术上必须做到：

1. 每个项目独立 `workspacePath`
2. 每个项目独立 `.buildwise/`
3. 迭代共享项目知识根
4. 项目 session 与迭代 session 分层

这是整个平台可持续沉淀的基础。

### 5.2 知识物化方案

知识必须区分：

- 事务型状态
- 可检索知识资产

建议长期固定以下落盘结构：

- `workspace.json`
- `project-summary.md`
- `ontology-business.md`
- `ontology-tech.md`
- `decisions.md`
- `release-history.md`
- `daily/*.md`
- `shards/*.md`
- `index/shards.json`

### 5.3 追溯与门禁方案

发布门禁不得只依赖分析摘要，应至少检查：

1. requirement refs 是否存在
2. boundary 是否确认
3. acceptance 是否映射测试矩阵
4. 测试矩阵是否执行
5. release review 是否生成阻断项

### 5.4 OpenClaw 集成方案

保持现有 Agent/session/workspace/skills/history 机制，不另起一套编排器。  
BuildWise 侧只负责：

- binding
- context injection
- policy constraints
- knowledge retrieval

## 6. 分阶段升级路径

### 阶段一：基线收口

目标：

- 执行版文档成型
- 模型和边界统一
- 例外对象可见

完成标志：

- 产品、架构、追溯、治理文档均可直接用于开发和评审

### 阶段二：主链验证收口

目标：

- analysis -> boundary -> test -> release 主链可稳定验证

完成标志：

- 契约测试与主门禁命令稳定通过
- 发布阻断原因可追溯

### 阶段三：运行时收口

目标：

- readiness、auth、metrics、prod-release 形成稳定口径

完成标志：

- 本地、预发、生产候选的验证链一致

### 阶段四：存量巨型文件治理

目标：

- 降低前端和应用层的大文件风险

完成标志：

- 超限文件持续减少
- 例外清单收缩

### 阶段五：知识系统增强

目标：

- 提升项目知识检索、每日汇总和跨迭代继承质量

完成标志：

- 项目知识库成为稳定上下文源，而非可选附属物

## 7. 风险清单

### 7.1 只改文档不改门禁

风险：

- 文档会再次失真

缓解：

- 文档变更必须伴随测试或脚本同步

### 7.2 只做运行时补丁不收口模型

风险：

- 项目知识、变更控制和发布链仍会继续漂移

缓解：

- 统一模型和追溯设计必须先于大规模功能扩展

### 7.3 把 OpenClaw 当作可无限侵入的内部模块

风险：

- 集成复杂度失控
- 后续演进成本陡增

缓解：

- 严守“不侵入内核、只做适配”原则

## 8. 验证策略

治理升级后至少验证：

1. 文档索引是否完整
2. 统一模型与代码命名是否一致
3. 边界守卫是否通过
4. 类型检查是否通过
5. 构建是否通过
6. 契约测试是否通过
7. 生产候选门禁是否通过

## 9. 回滚策略

若某次治理升级引发主链退化，回滚优先级如下：

1. 回滚新增门禁而不是放弃主门禁
2. 回滚具体实现拆分而不是回滚统一模型
3. 保留文档中已确认的真实设计结论，避免知识倒退

## 10. In Scope

1. 文档执行版重构
2. 模型和边界收口
3. 追溯与发布门禁收口
4. 运行时与知识物化收口
5. 存量大文件治理计划

## 11. Out Of Scope

1. 改变主产品航道
2. 新建多 Agent 平台
3. 重写 OpenClaw
4. 大规模 UI 美化
