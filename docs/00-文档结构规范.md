# 文档结构规范

## 目的

- 让 BuildWise 的产品、架构、研发治理和运行机制形成稳定的知识基线。
- 让任何新成员在 30 分钟内找到正确文档，并区分“当前事实”“理想目标”“历史材料”。
- 让文档成为实现、测试、脚本和运行门禁的同步约束，而不是事后补充说明。

## 范围

适用于仓库内所有长期维护文档：

- `docs/**`
- `v2/docs/**`
- `v2/backend/docs/**`
- 与运行、治理、接口、架构强相关的 `README.md`

不适用于：

- 临时会议记录
- 一次性调研草稿
- 未纳入主干索引的实验备忘

## 关键结论

1. 文档必须分层，不能把产品目标、技术实现、流程规则和运维操作写在同一篇文件里。
2. 文档必须声明“职责边界”，明确本文件负责什么、不负责什么。
3. 执行版文档优先级高于历史思考稿；当两者冲突时，以执行版为准。
4. 任何实现变更若影响产品行为、架构边界、模型结构、接口契约或门禁规则，必须同步更新对应文档。
5. 所有执行版文档默认控制在 1000 行以内；超过 700 行时应优先考虑拆分。

## 文档分层

### 1. 纲领与索引层

负责回答“去哪里找文档”和“哪些文档当前有效”。

适用目录：

- `docs/00-*`
- `docs/README.md`

这类文档只做：

- 索引
- 规范
- 角色说明
- 文档优先级定义

不得承担：

- 详细技术设计
- 详细产品流程
- 运维执行步骤

### 2. 产品与业务层

负责回答“平台服务谁、解决什么问题、主流程是什么、对象模型是什么”。

适用目录：

- `docs/10-*`

这类文档必须覆盖：

- 目标用户
- 核心业务链路
- 平台能力边界
- 非目标
- 成功标准

不得承担：

- 具体技术选型
- 代码目录设计
- 运行参数细节

### 3. 技术与架构层

负责回答“系统如何实现、边界如何划分、模型如何落地、追溯如何建立”。

适用目录：

- `docs/20-*`

这类文档必须覆盖：

- 架构原则
- 上下文划分
- 领域模型
- 数据与追溯结构
- 接口与边界约束

不得承担：

- 发布操作清单
- 业务宣传口径

### 4. 研发治理层

负责回答“团队如何开发、如何验证、如何治理例外、如何持续收口”。

适用目录：

- `docs/42-*`
- `docs/47-*`
- `docs/51-*`

这类文档必须覆盖：

- DDD/TDD 基线
- 质量门禁
- 文件规模治理
- 例外申请机制
- 升级路径与里程碑

### 5. 运行与投产层

负责回答“如何部署、验证、放行、回滚、运维”。

适用目录：

- `v2/backend/docs/**`

这类文档不得重复描述产品愿景和抽象架构原则，只保留运行事实和操作要求。

## 文件命名规则

### 1. 基本规则

- 文件名使用 `编号-标题.md`
- 编号按主题层次保留区间
- 标题必须表达单一职责，避免“综合说明”“补充汇总”这类模糊命名

### 2. 推荐编号区间

- `00-*`：索引、规范、声明
- `10-*`：产品、业务、用户流程
- `20-*`：架构、模型、技术设计
- `30-*`：交付流程、接口契约、自动化流程
- `40-*`：研发治理、质量、工程约束
- `50-*`：升级计划、系统性收口方案

## 执行版文档模板

所有执行版文档默认采用以下开头结构：

1. `目的`
2. `范围`
3. `关键结论`

随后进入正文设计内容。正文至少应包含：

- `In Scope`
- `Out Of Scope`
- `设计约束`
- `与其他文档的边界`

若文档涉及系统设计，还必须补充：

- `当前事实`
- `目标状态`
- `迁移策略`

若文档涉及治理规则，还必须补充：

- `执行方式`
- `例外机制`
- `校验命令`

## 文档边界要求

每篇文档都必须回答以下问题：

1. 本文档解决哪个问题。
2. 本文档不解决哪个问题。
3. 相关内容应该去哪篇文档看。

推荐使用固定段落：

- `范围`
- `不负责内容`
- `相关文档`

## 文档引用规则

### 1. 执行版优先

引用当前事实时，优先引用：

- 当前实现 README
- 执行版设计文档
- 后端运行文档

不要优先引用：

- 历史规划稿
- 商业构想稿
- 已被替代的升级草案

### 2. 链接要求

- 新增执行版文档必须被 `docs/README.md` 索引。
- 若一篇文档依赖另一篇文档中的定义，必须显式链接，而不是隐式假设。
- 若文档被替代，原文档必须写明替代关系或从索引中降级。

## 文档更新触发条件

出现以下变更时，必须同步更新文档：

1. 核心业务流程变化
2. 统一项目模型字段变化
3. 追溯结构变化
4. API 路由前缀、鉴权模式、发布门禁变化
5. DDD 边界或目录结构变化
6. 质量门禁命令变化
7. 生产要求、回滚要求或运行依赖变化

## 文档质量标准

### 1. 内容标准

- 使用明确结论，不使用模糊描述代替设计判断。
- 用“必须/禁止/允许/建议”区分强制性与建议性规则。
- 设计类文档必须给出结构、对象、关系和约束，不得只写口号。

### 2. 一致性标准

- 文档中的对象名称必须与代码中的主命名保持一致。
- 文档中的运行链路必须能在实现中找到对应模块。
- 文档中的门禁命令必须能实际执行或对应现有脚本。

### 3. 规模标准

- 单文档默认不得超过 1000 行。
- 700 行以上视为拆分预警。
- 单文档只承载一个主主题，避免“产品+架构+运维+计划”混写。

## 文档所有权

### 1. 产品层

默认由产品负责人或主设计者维护。

### 2. 技术架构层

默认由技术负责人维护，产品负责人参与边界确认。

### 3. 研发治理层

默认由技术负责人或工程治理负责人维护。

### 4. 运行与投产层

默认由后端负责人或运维负责人维护。

若当前没有专门角色，则由本仓库主维护者承担最终一致性责任。

## 决策记录要求

以下情况必须沉淀 ADR 或文末决策日志：

1. 技术路线改变
2. 领域边界调整
3. 门禁规则升级或降级
4. 例外白名单新增
5. 发布策略改变

决策日志至少包含：

- 时间
- 结论
- 原因
- 影响

## 禁止事项

- 禁止用单篇“万能说明”替代分层文档。
- 禁止在执行版文档中保留与当前实现明显不一致的内容。
- 禁止新增与现有职责重复的文档。
- 禁止只写“后续补充”“待完善”而不说明当前有效结论。
- 禁止把接口、脚本或门禁变化只留在代码里不更新文档。
