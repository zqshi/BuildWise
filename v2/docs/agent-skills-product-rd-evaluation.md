# Agent Skills Product R&D Evaluation

## 结论
当前 BuildWise 的 Agent+skills 模式在“治理骨架”上已经成立，但如果目标是高质量产品研发全环节，还存在两个关键缺口：

1. 缺少业务规则维度的专门建模与关联能力。
2. 缺少跨阶段的产品研发质量契约，无法证明 UX、原型、代码、测试之间的交接质量。

因此，原有 skills 是 `部分满足`，不是 `充分满足`。

## 当前已满足的部分
1. `00-orchestrator-sop`
   - 支持 Agent 自主编排 skills。
2. `01-ontology-mapping`
   - 支持工程本体和 traceability 建模。
3. `02-impact-analysis`
   - 支持影响面分析和风险分级。
4. `03-deliverable-governance`
   - 支持交付物状态治理。
5. `04-cross-iteration`
   - 支持跨版本继承与 delta 分类。
6. `06-quality-release-gate`
   - 支持发布判断。
7. `09-deliverable-content-contract`
   - 支持 PRD、设计规范、技术架构、代码、测试等交付物的内容完整性约束。

## 当前不满足的部分

### 1. 业务规则维度建模不足
现有 skills 能把需求映射到组件和代码，但不能完整回答：
1. 业务规则是什么
2. 谁定义了规则
3. 规则影响了哪些页面/状态/API/测试
4. 业务人员如何只用自然语言持续补充规则

这意味着“工程本体”存在，但“业务规则图谱”缺层。

### 2. 高质量产品研发全环节不足
现有内容契约能要求单个交付物更完整，但还不能系统检查：
1. PRD 是否真正支撑 UX
2. 原型与设计规范是否一致
3. 技术架构是否真的承接原型
4. 代码是否回溯到需求与业务规则
5. 测试是否覆盖业务规则变化

也就是说，单点交付物质量有约束，但跨阶段 handoff 质量不够强。

## 本轮升级

### 新增 `10-business-rule-linking`
职责：
1. 把业务人员的自然语言规则输入沉淀为：
   - 术语
   - 约束
   - 条件
   - 例外
   - 验收信号
2. 把这些规则关联到：
   - 页面
   - 组件
   - 接口
   - 状态机
   - 测试
3. 把高价值规则回写到项目 workspace 知识底座。

### 新增 `11-product-rd-quality-contract`
职责：
1. 检查高质量产品研发的全环节交接质量：
   - clarification
   - UX / prototype
   - engineering
   - testing
   - release
2. 不允许只因为交付物“存在”就放行下一阶段。
3. 强制检查 UX、原型、代码、测试之间的可追溯性。

## 升级后的双维建模

### 维度一：工程本体
由 `01-ontology-mapping` 主导。

内容包括：
1. 页面
2. 组件
3. 接口
4. 数据结构
5. 状态机
6. 代码路径
7. 测试对象

### 维度二：业务规则
由 `10-business-rule-linking` 主导。

内容包括：
1. 领域术语
2. 规则约束
3. 判定条件
4. 例外逻辑
5. 合规口径
6. 验收口径

### 质量检查层
由 `11-product-rd-quality-contract` 主导。

目标：
1. 检查前后环节是否真正承接
2. 检查 UX -> 代码 -> 测试 是否闭环
3. 检查业务规则是否进入实现与验证

## 对产品方向的判断
如果：
1. Agent 推理能力足够
2. 工程本体清晰
3. 业务规则可持续灌入
4. 有质量门禁和审计追踪

那么业务人员确实可以：
1. 用自然语言说明需求
2. 推进页面和交互开发
3. 持续灌入领域知识
4. 在不直接依赖研发改代码的前提下，完成大部分完整链路

但这不是“只有模型强就够了”，而是 `模型 + 本体 + 规则 + 质量契约 + 治理门禁` 一起成立。
