# BuildWise

> 把需求、规则、交付物和发布决策，收进同一个会持续变聪明的 AI 交付工作台。

BuildWise 面向产品经理、业务负责人、技术负责人和 QA。  
它不是又一个“会聊天的生成器”，而是一个把**需求分析、领域建模、交付物推进、测试验证、发布评审、项目知识沉淀**串成闭环的 AI 原生软件交付系统。

它想解决的不是“再写一份文档”，而是软件团队最难回答的三个问题：

- 这次需求到底影响了哪些页面、接口、规则和发布风险？
- 当前版本到底能不能发，凭什么发？
- 做过一轮又一轮之后，团队到底有没有真正把业务知识沉淀下来？

## 为什么它值得看

大多数团队的问题不是“没人会写文档”，而是：

- 需求改了，但没人知道影响了哪些页面、接口和规则
- 上线前没人敢回答“现在到底能不能发”
- 版本做了一轮又一轮，规则、边界和历史决策都散落在聊天、PRD、原型和代码里
- 业务人员能提需求，却很难持续参与“规则建模”和“版本决策”

BuildWise 试图解决的，正是这条从“业务意图”到“工程落地”之间长期断裂的链路。

你给它的是：

- 自然语言需求
- PRD / Word / PDF / 截图 / 原型 / HTML
- 历史版本背景

它输出的是：

- 结构化分析与澄清问题
- 项目级业务实体、规则、关系和约束
- PRD、设计规范、技术架构、代码交付、测试矩阵、发布评审
- 基于证据的 `go / caution / block` 决策
- 可持续沉淀的项目知识库

## 产品价值

### 1. 业务人员能直接推进软件交付

BuildWise 把“产品想法 -> 需求澄清 -> 交付物 -> 测试 -> 发布”做成一个工作台，而不是要求业务人员先学会研发过程语言。

### 2. 项目越做越懂业务

每个项目都有独立 workspace。  
所有迭代持续回写到同一个项目知识空间，沉淀：

- 业务术语
- 稳定规则
- 实体关系
- 页面/API/代码映射
- 决策日志
- 已知风险
- 变更模式

### 3. AI 不只是生成内容，而是参与治理

BuildWise 当前实现的是 `Agent + Skills` 模式：  
AI 会根据当前阶段、项目知识和用户对话动态选择技能，而不是死板地跑固定流程。

### 4. 发布决策不再靠拍脑袋

每次迭代都会进入：

- 变更边界确认
- 测试矩阵
- 发布评审

系统会明确告诉你：现在可以发、谨慎发、还是必须阻断。

## 当前已落地能力

当前仓库不是概念稿，已经落成前后端一体的工作台，包含：

- 官网入口、登录、仪表盘、项目工作台
- 项目 / 迭代管理
- 需求材料上传与分析
- 项目建模与领域建模
- 交付物抽屉与卡片化预览
- 代码类交付物的结构化展示
- 测试矩阵与发布评审
- 项目级 workspace 隔离
- OpenClaw 非侵入式集成
- 项目知识目录 `.buildwise/` 物化、分片和检索

## BuildWise 和常见 AI 工具的区别

- 它不是单轮问答工具，而是项目级持续交付空间。
- 它不只生成“内容”，还维护规则、边界、证据和发布决策。
- 它不把知识留在会话里，而是回写到项目 workspace。
- 它让业务人员可以持续参与建模，而不需要先学会技术实现语言。

## BuildWise 的工作方式

```text
主窗口配置默认策略
        ↓
每个项目绑定独立 workspace
        ↓
项目内创建迭代并上传需求材料
        ↓
AI 完成分析、澄清、边界收敛
        ↓
生成并推进交付物、测试和发布评审
        ↓
规则、本体、证据与决策回写项目知识库
```

这意味着：

- `Project` 是长期知识边界
- `Iteration` 是项目内版本上下文
- `Workspace` 是项目运行边界，不是临时会话容器

## 适合谁

- 产品经理：分析需求、确认边界、审核交付物
- 技术负责人：审查规则映射、影响范围、发布门禁
- QA：执行测试矩阵、校验阻断项
- 业务负责人：查看项目全景、追问规则和风险

## 快速启动

环境要求：

- Node.js `>= 22`
- npm `>= 10`

```bash
cd v2
npm run install:all
npm run dev:stack:start
```

默认入口：

- 官网：`http://localhost:5173/#/`
- 仪表盘：`http://localhost:5173/#/dashboard`
- 后端：`http://127.0.0.1:5055`

## 质量门禁

```bash
cd v2
npm run verify:all

cd backend
npm run verify:prod-readiness
```

说明：

- `verify:all` 是前后端聚合校验
- `verify:prod-readiness` 是后端投产门禁
- 当前分支已通过本地发布候选门禁，但最终生产放行仍取决于生产配置、SQLite 链路与部署环境校验

## 当前状态

当前 `codex/prod-governance-rc` 分支可以视为**可受控投产候选**：

- 核心边界门禁、构建、类型检查和 contract 已通过
- 项目级 workspace 隔离、项目知识目录和 OpenClaw 非侵入式适配已经落地
- 运行时语义、健康检查、就绪检查、鉴权默认行为和文档口径已经收口

这并不意味着“可以跳过上线流程”。  
真正放生产前，仍需按后端生产文档确认：

- `AUTH_MODE=jwt`
- `JWT_SECRET`
- `CORS_ORIGINS`
- `VITE_API_BASE`
- 独立 `workspacePath`
- `.buildwise/` 备份策略

## 文档策略

`docs/` 下保留了愿景、商业计划、升级方案和执行规范等多类文档。  
其中一部分属于历史方案或阶段性治理记录，不应当作当前运行事实的唯一来源。

当前以这三类文档为准：

1. 根 README：对外产品定位与总览
2. `v2/README.md`：前端/工作台运行与演示说明
3. `v2/backend/README.md` 与 `v2/backend/docs/*`：后端、接口、投产与运维口径
